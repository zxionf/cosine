# ui-widget #1 Widget 类评估：过重、复用差、扩展差（2026-11-27 14:27 CST）

> 基线：main@167a3f83（HEAD 含 `review: 设计`）  
> 短哈希：167a3f83  
> 工作区：dirty（`src/ui/widget.hpp` 未提交：`x()/y()/width()/height()` 去掉了 `virtual`；本文档为另一处新增）  
> 快照文件：ui-widget-#1-261127-142712-167a3f83.md  

> **口径**：只读评估。**未修改任何代码，未提交任何东西**。所有数字来自 `grep`/`wc` 与一次
> 临时 `sizeof` 实测（程序已删除）。凡属"潜在缺陷"均显式标注，不冒充已复现 bug。

## 0. 结论摘要

`ui::Widget` 是**一个承担 9 类职责、145 个成员函数、50 个虚函数、36 个数据成员、固定 280 字节
基类开销**的上帝基类。它不是"抽象得不够"，而是**抽象得太低**：把"几何 + 树 + 输入 + 焦点 +
样式 + 主题 + 盒模型 + 层叠 + 诊断"全塞进一个类，于是复用只能靠继承、扩展只能靠改基类。

| 维度 | 判定 | 一句话依据 |
|---|---|---|
| 体积 | ❌ 过重 | 630 行头文件 + 162 个内联函数体；`sizeof(Widget)` = **280 B**，连 `Spacer` 也付 |
| 职责数 | ❌ 9 类 | 见 §2，每类都有独立成员群与入口 |
| 复用性 | ❌ 差 | 复用单位是"继承 Widget"，无行为组合；`arrange()` 有 **20/35 个是纯样板** |
| 扩展性 | ⚠️ 差 | 加交互要改基类（39 个 TU 重编）；**14 个虚函数全仓从未被覆写**（假扩展点） |
| 契约可靠性 | ⚠️ 弱 | 半实现 Composite（`add()` 运行时抛异常）、`children_` 被 shadow、14 处绕过 `set_geometry` |
| 横切关注点 | ❌ 分散 | `enabled_` 在 8 个控件各存一份、`pressed_` 13 处赋值、焦点环 13 处手写 |

**三句话总结**：

1. 想加一个"可悬停、可禁用、有焦点环、能变色的方块"，今天必须复制一份 `ColorRect` 再抄
   4 个事件钩子 + 焦点环 + `control_state()` 调用 —— 因为这些能力不是基类提供的**组合单元**，
   而是散落在 `Widget` 的 50 个虚函数与各控件的私有字段里。
2. 想加一种交互（比如"滚轮横向滚动"）必须改 `widget.hpp` → 39 个编译单元重编；而 14 个
   已有虚函数从来没被任何子类覆写过 —— 扩展点是"多但错"。
3. 复用与扩展的瓶颈都不在"缺少模式"，而在**基类把可变点与不变点混在一起**：不变的
   （几何存取、脏标记、测量缓存）应下沉成工具/组件；可变的（控件长什么样、响应什么）应上提成
   窄接口或组合件。

## 2. 复用性：为什么"可复用"在今天是空话

### R1（阻断级）复用单位是"继承整个 Widget"，没有可组合的行为单元

今天要新增一个"彩色方块"，最省事的做法是复制 `ColorRect`（66 行）。因为下面这些能力
**都不是可复用的组件**，而是"基类虚函数 + 各控件自己实现"：

| 能力 | 今天怎么获得 | 复用成本 |
|---|---|---|
| 悬停变色 | `is_hovered()`（基类给）+ 自己 `if` 或 `control_state()` | 每个控件各写一遍（`visual_style` 25 处调用） |
| 按下反馈 | 自己的 `bool pressed_` + 4 个钩子里的赋值 | 3 个控件 13 处赋值（`pressed_ = true/false`） |
| 禁用态 | 自己的 `bool enabled_` | **8 个控件各存一份**（`button/checkbox/radio/slider/dropdown/drag_float/color_input/text_input`） |
| 焦点环 | `append_focus_ring(list, bounds, radius)` | 13 处手写调用 |
| 边框/圆角 | `corner_radius(style.radius)` + `append_rounded_ring` | 每个控件 3~6 行 |
| 悬停/离开跟踪 | `UISystem` 会自动 `set_hovered`（这点是对的） | ✅ 唯一免费的横切能力 |

`enabled_` 的例子最能说明问题：**禁用是一个语义，不是一种外观**。它在 8 个控件里各存一份
布尔，意味着：

- 无法统一 API（`widget->set_enabled(false)` 不存在，只能 `dynamic_cast` 到具体类型）；
- 无法统一保证（谁能保证每个新控件都记得把 `enabled_` 映射成 `ControlState::Disabled`？）；
- 组合情形无解（"禁用 + 选中"没有基类表达）。

### R2（阻断级）`arrange()` 的 20/35 是纯样板，`measure()` 缺少模板

全仓 35 个声明 `arrange(Rect slot) override` 的控件里，**20 个函数体只有 `set_geometry(slot);`**：

```
button checkbox collapsible_header color_input color_rect drag_float image label
preview_ruler progress radio slider spacer tab_bar text_input tooltip
file_browser list_view scene_view timeline_view           → 20 个
```

也就是说：**超过一半的子类复写的方法体是同一行**。这不是"模式"，这是基类少给了一个默认实现。

`measure()` 同样有样板化倾向：

```cpp
// color_rect / image / list_view / dropdown / menu_bar 都是这个形状
glm::vec2 measure(glm::vec2) override { return clamp_size(preferred_size()); }
```

基类已经有 `preferred_size_`、`clamp_size()`、`set_preferred_size()`，却没有提供
"叶子默认 measure = clamp(preferred_size)" 的默认实现，于是 5 个以上的控件重复写这一行。

### R3（高）两套测量缓存，且基类那套几乎没人能用

| 缓存 | 位置 | 使用者 |
|---|---|---|
| 基类：`measure_cache_hit` / `store_measure`（约束 + 布局轮次） | `widget.hpp:534-550` | **只有 2 个容器**（`scroll_panel`、`tab_view`） |
| `Label` 自己的 `MeasureKey` + `MeasureCache`（文本 + 字号 + 换行宽 + 图集指针） | `label.hpp:180-200` | `Label` |
| `TreeView` 自己的 `cached_visible_rows()` | `tree_view.hpp` | `TreeView` |

三套缓存的存在说明基类那套**键太窄**（只有 constraints + epoch），装不下"文本/字号/换行宽"
这类派生度量。而复用者面对的是："到底该用哪套？哪套和脏标记联动？"——没有文档回答。

### R4（中）焦点环、禁用、按下、选中四类语义，各自散落

```
enabled_      8 处声明
pressed_     13 处赋值（button 4 / checkbox 5 / dropdown 4）
selected_     4 处（table/tree_view/tab_bar/checkbox?）
焦点环       13 处调用
```

基类只统一了 **hover** 与 **focus** 两个布尔（`hovered_`、`focused_`），其余全部靠各控件自觉。
UI-40 已经把"颜色"这一层收敛进 `StyleRole`（好），但**状态本身**没有收敛。

### R5（中）`protected` 数据 + `virtual` 访问器 = 两个真相

`children_` 是 `protected` 成员，同时 `children()` 是虚函数。两者可以不一致，而且已经不一致：

```cpp
// section.hpp:44 —— 返回内部 Vbox 的 children，基类那份 children_ 是空的
const std::vector<std::unique_ptr<Widget>>& children() const override { return content_->children(); }

// preview_pane.hpp:72 —— 子类又声明了一个同名 children_，把基类的 shadow 掉
std::vector<std::unique_ptr<xel::ui::Widget>> children_;
```

后果见 §4（结构裂缝 C1/C2）。这类"既给数据又给虚访问器"的设计，等于允许子类在
"用基类存储"和"自己存储"之间任选，而基类内部两种写法混用（4 处遍历点里 2 处用虚访问器、
2 处直接用成员）。

### R6（低）头文件内联函数体过多

`widget.hpp` 里几乎所有小函数都是内联，导致任何一处实现改动都触发 39 个 TU 重编。
`widget.cpp` 只承载了样式过渡与焦点环（183 行）。这不是性能问题，是**编译耦合力问题**。

## 3. 扩展性：为什么"加东西"很难

### E1（高）14 个虚函数全仓从未被覆写 —— 假扩展点

| 从未被覆写的虚函数 | 数量 |
|---|---|
| `set_pos` / `set_size`（各 2 个重载）/ `set_global_bounds` | 5 |
| `parent()` / `clips_children()` / `debug()` | 3 |
| `padding_left/right/top/bottom` | 4 |
| `margin_left/right/top/bottom` | 4 |

`src` + `examples` + `test` 全仓搜索 `override` 命中数 = **0**（工作区基线）。

这些 `virtual` 传递了一个错误信号："你可以覆写它们"（比如"我想自定义 padding 计算"），
但实际上没有任何子类这么做过；而 `clips_children()` 是**派生自 `overflow()` 的纯计算**，
它被设成 virtual 只会让"覆写它"和"覆写 `overflow()`"两条路打架。

> 工作区里 `x/y/width/height` 已从 virtual 参数表里摘掉（未提交），方向正确；本节列的 14 个
> 是同一类问题剩下的部分。

### E2（高）加一种交互 = 改基类 = 39 个 TU 重编

18 个 `on_*` 钩子平铺在 `widget.hpp`，没有分组、没有能力声明。想加"滚轮横向"、"拖拽开始/
结束"、"右击菜单"这类事件，只能往基类再加一个虚函数：

- 编译面：39 个 TU（35 个 ui 内部头文件 + 3 个 test + 自身）；
- 语义面：新钩子是返回 `bool`（可消费）还是 `void`？现有两派并存（见下）；
- 一致性面：`UISystem::dispatch` 要同步加分支，`event::InputEvent::Type` 要同步加枚举。

现有钩子的返回类型分布（说明"消费语义"没有统一契约）：

```
bool：on_mouse_move on_mouse_down on_mouse_up on_click on_right_click
      on_double_click on_long_press on_scroll on_key_down on_key_up on_char   → 11
void：on_hover on_mouse_leave on_mouse_enter on_focus_gained on_focus_lost    → 5
```

### E3（高）半实现 Composite：`add()` 运行时抛异常

```cpp
virtual void add(std::unique_ptr<Widget> child)
{
    (void)child;
    throw std::logic_error("Widget::add is not supported by this widget");
}
```

- 叶子控件走 `add()` → **运行时**异常（而不是编译期类型错误）；
- 但 `children()` 对所有控件都存在并返回 `children_`（叶子恒空）；
- 于是"这是不是容器"这件事**没有任何类型或方法可用**，只能靠"试一下/读文档/看源码"。

对比：`ListView` 用纯虚 `item_count()/draw_row()` 表达"我是列表"，接口窄而明确 —— 这说明
本仓有能力做窄接口，只是 `Widget` 没做。

### E4（中）契约靠注释与纪律，编译器不参与

| 契约 | 违反现状 | 检测手段 |
|---|---|---|
| 布局写入必须走 `set_geometry()` | **14 处**直接写 `global_`（`window.hpp` 6、`widget.hpp` 3、`menu_bar` 2、`scrim`/`collapsible_header`/`scroll_view` 各 1） | 无（代码评审） |
| 子项挂载必须走 `adopt()` | **3 处**直接 `children_.push_back`；`Section` 干脆不 adopt | 无 |
| 同一帧内同一 `StyleRole` 只能用一个 state | 已在 UI-46 踩过（滚动条滑块与槽互相覆盖） | 靠新加的测试，无断言 |
| `measure()` 返回值 ≤ constraints | 靠 `measure_child()` 兜底 clamp | 部分有测试 |

`set_geometry()` 与 `global_` 直写并存，是最典型的"基类没有独占不变量"：它想保护 `local_`
与 `global_` 的同步，但成员是 `protected`，14 处绕过了它。

### E5（中）"能力"无法声明：可滚动、可禁用、可聚焦都不可查询

```cpp
widget->focusable();      // 有
widget->hit_testable();   // 有
widget->set_enabled(?)    // 没有 —— 8 个控件各自实现
widget->scrollable(?)     // 没有 —— 只有 ScrollView / ListView / TextInput 内部有 ScrollState
```

想在通用代码里写"如果这个控件禁用就跳过"，只能 `dynamic_cast`。这是"基类承担了 42 个子类的
公共部分，却漏掉了真正的公共语义"的直接后果。

## 4. 结构裂缝（可能出 bug 的地方）

以下均标注**已确认**（代码可见）与**潜在**（需实测/触发条件）。

### C1（已确认，潜在后果）`Section` 未 adopt 内部 Vbox → 脏标记链断点

```cpp
// section.hpp:26-32 —— content_ 是裸成员，从不 adopt()，也从不 set_parent()
content_ = std::make_unique<Vbox>(...);
// section.hpp:38-42 —— add() 转发给 content_，基类 children_ 永远为空
void add(std::unique_ptr<Widget> child) override { content_->add(std::move(child)); … }
```

`Widget::mark_layout_dirty()` 的传播是 `parent_` 链：

```cpp
if (parent_) parent_->mark_layout_dirty();
```

`content_->parent_ == nullptr`，所以 **Section 内容子树里的任何变更都会在 `content_` 处
断链**：Section、它的父容器、`UIRoot` 都不会被标记为 dirty。而 `UISystem::tick` 是门控的：

```cpp
if (resized || root_->layout_dirty()) { root_->layout(); … }     // ui_system.cpp:150
```

触发条件：Section 内容的尺寸发生变化（如内部 Label 换文本、Table 增行）且没有其他 dirty 源。
当前 `Section` **在 src 中无实际使用点**（仅注释与主题字段提及），所以是"未爆的雷"，不是现行 bug。
佐证：`examples/ui_lab/main.cpp:711-713` 的注释写着"内容重建后立刻重排：只标 dirty 要等下一帧"，
随后直接调 `root->layout()` —— 说明团队已经与这类"标了 dirty 但不生效"的现象打过照面。

### C2（已确认）`PreviewPane` shadow 了基类 `children_`

```cpp
// preview_pane.hpp:72
std::vector<std::unique_ptr<xel::ui::Widget>> children_;   // 与 Widget::children_ 同名
```

基类 `children_` 与之并存，`adopt()` 会往**基类那份**里推，而所有遍历走 `children()`（虚）
拿到的是**派生那份**。一旦有人对该控件调 `adopt()`，两份存储立刻分叉。

### C3（已确认）4 个遍历点，2 种取子方式

| 遍历 | 取子方式 |
|---|---|
| `set_context` | `children()`（虚） ✅ |
| `sorted_paint_order` / `layer_paint_order` | `children()`（虚） ✅ |
| `clear_layout_dirty_recursive` | `children_`（成员） ❌ |
| `invalidate_measure_recursive` | `children_`（成员） ❌ |

对 `Section` 这种"`children()` ≠ `children_`"的控件：主题/密度切换（走
`invalidate_measure_recursive`）**不会**失效其真实子树的测量缓存。当前靠两件事掩盖：
布局轮次 `layout_epoch` 让跨轮缓存必然 miss、`Label` 的缓存键含字号。属于"设计上不一致，
被其他机制兜住"。

### C4（已确认）同一棵树，不同遍历的覆盖面不一致

双容器（`children_` + `overlays()`）的真正代价是：**每个遍历点都必须自己记住“两处都要走”**，
而现有遍历点的覆盖面并不一致：

| 遍历 | 覆盖 overlays |
|---|---|
| `set_context` / `layer_paint_order` / `collect_hit_path` / `update_tree` | ✅ |
| `clear_layout_dirty_recursive` / `invalidate_measure_recursive` | ✅ |
| `debug_recursive()`（`widget.hpp:216-220`） | ❌ 只走 `children()` |
| `paint_order()`（`widget.hpp`） | ❌ 只走 `children()`（另有 `overlay_paint_order`） |

（`mark_layout_dirty()` 的传播没问题：`add_overlay()` 会给 overlay 设 `parent_`。）

所以 `debug_recursive()` 开了调试框后，overlay 子项不会被递归开启。这是“双容器 + 人工两处写”的
必然结果：只要将来再加一个遍历，就得再记一次。UI-34/UI-45 修过的“`clear_layout_dirty` 未递归”
是同一结构的另一面。

## 5. 与历史缺陷的对应：三次事故都落在这张表的同一行

| 事故 | 根因落点 | 本报告的对应项 |
|---|---|---|
| `clear_layout_dirty` 只清自己 → `set_pos()` 后 root 不再 dirty | 基类遍历不完整、依赖派生类自觉 | **C3 / C4** |
| 密度切换只缩放部分字段，checkbox/scrollbar 不跟随 | 横切状态无统一入口 | **R4**（禁用/按下/选中同型） |
| 滚动条滑块与槽同色消失 | 过渡槽按 role 索引，无"一帧一角色"契约 | **E4**（契约靠注释） |

共同模式：**基类拥有状态与遍历，但不拥有不变量**。修一次坏一次，因为没有任何机制阻止
"下一个人再用另一种方式访问同一份状态"。

## 6. 重构选项

### A. 拆能力接口（接口隔离）

```cpp
struct PointerTarget { virtual bool on_mouse_down(...) = 0; ... };
struct KeyTarget     { virtual bool on_key_down(...) = 0; ... };
struct LayoutElement { virtual glm::vec2 measure(...) = 0; virtual void arrange(Rect) = 0; };
class Widget : public LayoutElement, ...(只组合实际用到的目标)
```

- 收益：基类虚函数从 50 → 每类 3~8 个；控件只依赖它真正实现的能力；新交互加新接口、不动旧类。
- 成本：**破坏性**，42 个子类都要调整；`UISystem` 的 dispatch 需要 `dynamic_cast`/类型标签定位目标。
- 风险：多继承 + 交叉转换，若设计不严会引入更难的 bug。

### B. 组合优于继承：把"盒模型 + 样式 + 悬停"拆成可复用部件

```cpp
class ColorBox : public Widget {           // 只负责"画一个矩形"
    BoxVisual visual_;                     // 样式角色 + 过渡（组合，可复用）
};
```

- 收益：悬停/禁用/焦点环/过渡成为**部件**而不是基类虚函数；复用变成"装配"。
- 成本：中等；需要先定义 3~5 个部件（`BoxVisual`、`TextVisual`、`HoverState`、`FocusRing`）。
- 与现状兼容：可以先让新控件用部件，老控件不动。

### C. 只做减法（推荐先做）

| 动作 | 改动量 | 收益 |
|---|---|---|
| 删 14 个从未被覆写的 `virtual` | 小 | 虚函数表 50 → 36；消除"假扩展点"；编译面不变但语义清晰 |
| 把 `arrange()` 的纯样板下沉成基类默认实现 | 小（20 个控件各删 4 行） | 新增叶子控件从"实现 3 个方法"降到 2 个 |
| 提供 `LeafWidget` 中间基类（= `arrange = set_geometry` + `measure = clamp(preferred_size)`） | 小 | 20 个叶子直接继承，样板归零 |
| `set_geometry()` 独占不变量：`global_`/`local_` 改 `private` + `protected` 只读访问器 | 中（14 处绕过要改） | 编译器开始帮忙守契约 |
| `enabled_` 上提基类 + `set_enabled()` / `is_enabled()` + 统一映射 `ControlState::Disabled` | 中（8 个控件删字段） | 横切语义统一，通用代码可判断 |
| 统一 `children` 取子方式（要么全用虚访问器、要么全用成员） | 小 | 消除 C3/C4 类隐患 |

### D. 维持现状 + 加护栏

- 为 `set_geometry`/`adopt` 加 `#ifndef NDEBUG` 断言（检测"直写 global_"难，但检测"parent 不一致"容易）；
- 为"一帧一角色一状态"加调试断言；
- 给 `StyleTransition` 的 1,688 B 加注释说明取舍。

### 推荐路线

1. **先做 C**（低成本、非破坏性、可增量）：减法 + `LeafWidget` + `set_geometry` 私有化 +
   `enabled_` 上提。预计 `Widget` 虚函数 50 → 34 左右，42 个子类中约 20 个显著变短。
2. **再做 D**（护栏），保证 C 之后不再回潮。
3. **把 B 作为中期目标**：新控件用部件装配，老控件逐步迁移。
4. **A 最后做，且与 UI-37（布局 setter 17→10）合并**：两者都是"基类接口收敛"，分开做会
   互相冲突（`set_pos/set_size/set_flex_grow/...` 正是 A 要拆的东西）。

## 7. 建议排序（按 收益/成本）

| # | 建议 | 成本 | 收益 | 破坏性 |
|---|---|---|---|---|
| 1 | 删 14 个死虚函数 | 极低 | 虚表 50→36，语义清晰 | 无（无人覆写） |
| 2 | `LeafWidget` 中间基类 + 下沉样板 `arrange` | 低 | 20 个控件各减 4~6 行；新控件少实现 1 个方法 | 无 |
| 3 | 统一 `children` 取子方式 | 低 | 消除 C3/C4 类结构裂缝 | 无 |
| 4 | `global_`/`local_` 私有化 + 改 14 处绕过点 | 中 | 编译器开始守"几何只能经 set_geometry" | 轻（内部） |
| 5 | `enabled_` 上提 + `set_enabled()` | 中 | 统一禁用语义；通用代码可查询 | 轻（8 个控件） |
| 6 | `StyleTransition` 取舍注释（或共享表） | 极低 / 中 | 记录 1,688 B 的成本 | 无 |
| 7 | 部件化（`BoxVisual` / `HoverState` / `FocusRing`） | 中高 | 复用从"继承"变"装配" | 无（增量） |
| 8 | 能力接口拆分（A） | 高 | 基类虚函数按能力切分 | **破坏性** |

## 8. 结论

- **"过重"是可量化的**：145 个成员函数、50 个虚函数、36 个数据成员、280 B 固定开销、
  9 类职责。且这个重量是**每个控件都要付**的（`Spacer` 288 B，其中 280 B 与"画一个空"无关）。
- **"复用差"的根因不是缺设计模式，而是复用单位太粗**：要么继承整个 `Widget`（连带 9 类职责），
  要么复制粘贴（20 个控件的 `arrange` 就是复制粘贴的产物）。
- **"扩展差"的根因是扩展点放错了位置**：18 个事件钩子平铺、14 个虚函数无人使用、
  `add()` 运行时抛异常、能力不可查询 —— 真正的扩展需求（新交互、新状态、新外观组合）
  反而没有入口。
- 好消息是：**修复路径不需要大重写**。§6-C 的六项都是非破坏性增量，能在一到两个 task 内
  把虚函数数量、样板行数、结构裂缝同时压下去；破坏性的能力接口拆分（A）应留到最后，
  并与 UI-37 合并推进。
- 一句话：**`Widget` 需要的是"减法 + 分组"，不是"再加一层抽象"。**
