## 0. 结论摘要

`src/ui`（82 文件 / 13,816 行 / 46 个控件类）在过去一周完成了一次真实的重构：状态、样式、语义、
测量缓存、主轴解算都收敛成了**单一所有者的值类型**，这是本轮评估里最扎实的部分。
但**"容器族"和"节点分层"这两处抽象仍停在半成品状态**：一个没有任何子类的 `ContainerNode`、
一个只有一种实现的 `LayoutNode`、以及三个各自重抄五类仪式的流式容器。

| 维度 | 判定 | 一句话依据 |
|---|---|---|
| 抽象：状态 / 语义 / 样式 | ✅ 到位 | `Interaction` / `Semantics` / `VisualState` / `MeasureCache` 四个值类型 + 架构断言（K1/K6/K7）守着 |
| 抽象：布局内核 | ✅ 基本到位 | `resolve_main_axis` 只有一份；`measure_child` 是唯一协商入口（但 `Section`/`Window`/`ScrollView` 三个宿主共 5 处直调 `measure`） |
| 抽象：节点分层 | ⚠️ 过度且未闭合 | `Node` 把 `measure/arrange/...` 声明为**纯虚**，全仓只有 `LayoutNode` 一个实现 → 抽象为省一次转型，代价是 14 次 `as_layout()` + 39 次 `child_at()` |
| 抽象：容器族 | ❌ 未到位 | `ContainerNode` **0 个子类、0 个 `is_container()` 调用**；`Vbox/Grid/Wrap` 不继承它，各自重写 `add/layout/append_to/set_context` |
| 抽象：复合控件 | ❌ 缺原语 | `Section`（header 不在树里）/`Window`（body、footer）/`ScrollPanel`（content）都要手工 `set_context` + 手工 `arrange` 隐藏子节点 |
| 复用 | ⚠️ 主轴成功、仪式失败 | 主轴解算 4 份 → 1 份（`Vbox`/`Hbox` 共用 `LinearLayout`）；交叉轴 stretch/aspect/clamp 仍 3 份、主题注入 5 份、缓存前言 5 份、`find_root` 4 份 |
| 扩展性：加叶子 | ✅ 好 | `LeafNode` + 66 行（`Tag`）即可；18 个叶子 0 个覆写 `arrange` |
| 扩展性：加容器 / 复合 | ❌ 贵 | 新容器 ≈400 行，其中 ≈150 行是抄来的；复合控件没有"chrome + content"原语 |
| 扩展性：加事件 / 主题令牌 | ⚠️ 中 | 加事件要改 `layout_node.hpp`（39 虚拟函数预算只剩 6 个空位）+ `UISystem::dispatch`；加令牌要改 3~4 处 |
| SRP | ⚠️ 基类混职责 | `LayoutNode` = 布局 + 交互 + 样式过渡 + 语义 + Tab 顺序 + 调试；`UIRoot` = 布局 + overlay + 模态栈 + 焦点钩子 + trash |
| OCP | ⚠️ 半边 | 角色表（`Theme::style`）是真 OCP（加角色不动控件）；容器/事件/复合是"要改基类或复制实现" |
| LSP | ⚠️ 有风险 | `as_layout(Node*)`/`measure_child(Node&)` 用 `static_cast`，靠"所有 Node 都是 LayoutNode"这条**注释级**不变量 |
| ISP | ❌ 宽接口 | 39 个基类虚函数、16 个事件钩子（`bool`×11 / `void`×5）全量继承；Q1 已量化否决拆分，但代价仍在 |
| DIP | ⚠️ 部分 | `UIContext` 走父链 + 全局回退（`ui::theme()` / `active_font_atlas()`）；`UISystem` 直接 include `composites/window.hpp` 做窗口热区 |
| DRY | ⚠️ 中 | 见 §4 的 10 类重复；主轴/缓存/语义/绘制四类已成功收敛 |
| YAGNI | ❌ 一处 | `ContainerNode`（+ `is_container`）是纯粹的空转抽象，还被 `test_ui_architecture` 当成结构契约锁住 |
| 组合优于继承 | ⚠️ 参半 | 4 个部件（`layout_/box/input/visual`）+ `paint::` 自由函数方向正确；但 `LayoutNode` 仍把三种能力塞进一条继承链 |

**三句话**：

1. **该抽象的已经抽象对了**——状态、语义、样式槽、测量键、主轴预算、绘制函数都是"小而单责、可被断言"的单元，
   这是本轮最值钱的部分，且已被 `test_ui_architecture` 的 24 条 `check()` 变成不可回退的契约。
   （注：`docs/todo-ui.md` 记的是「32 条断言」，实测 `check()` 调用 24 处 —— 文档计数漂移，见 §9。）
2. **该抽象的没抽到位**——"容器"和"复合控件"这两个真正高频变化的东西没有抽象：`ContainerNode` 是空壳，
   `Section`/`Window` 用私有成员 + 手工 `arrange` 模拟容器，于是新增一个容器要抄 150 行、新增一个复合控件要抄一套托管逻辑。
3. **抽象得过头的地方在 `Node`**：为了"遍历时不必向下转型"，把布局契约放到 `Node` 上声明为纯虚，
   结果得到一个永远只有一个实现的抽象，以及 14 处 `as_layout()` 反向补偿——净收益接近零。

## 3. 抽象评估

### 3.1 到位的抽象（应保留并推广）

| 抽象 | 位置 | 为什么算"到位" |
|---|---|---|
| `Interaction` | `input/interaction.hpp`（6 bool + `state()`） | **状态的单一所有者**；`ControlState` 优先级只有一份；K1 断言"没有 per-widget `enabled_`" 守住 |
| `Semantics` | `semantics/semantics.hpp` | **派生只读视图**，不存第二份真值；`role_is_checkable/editable` 由 role 纯派生，避免"每个控件写一个虚函数" |
| `VisualState` / `StyleSlot` | `style/visual_state.hpp`、`widget_style.hpp` | 过渡缓存从 1,688 B + 堆分配降到 **104 B 内嵌**；按 role 分槽，一个控件一帧可请求多个角色；`revision` 做整组失效 |
| `MeasureCache` / `MeasureKey` | `layout/measure_cache.hpp` | 3 套缓存（基类 / Label / TreeView）收敛成 1 套；派生输入用 FNV-1a 哈希避免每控件 32 B 字符串 |
| `resolve_main_axis` | `geom/layout_budget.hpp` | 主轴 pct 预算 + flex grow/shrink **只写一次**；`LinearLayout`（82 行头 + 296 行实现）承载全部流程，`Vbox`/`Hbox` 各只剩 18 行（构造 + 选轴） |
| `paint::` 四个纯函数 | `style/painters.hpp` | 零状态、零虚函数、可内联；焦点环实现只剩一份 |
| `LayoutSpec` 单写入口 | `node/layout_node.hpp`（K7） | 布局意图只有一种数据形态，`layout_.` 直写只允许出现在 2 个函数 |
| `UISystem::Target`（指针 + 生命周期令牌） | `system/ui_system.hpp` | 悬垂指针问题用 `weak_ptr` 令牌解决，比"额外维护一张存活表"更内聚 |
| `UIContext` 的 theme revision | `system/uicontext.hpp` | 主题可变性边界闭合：只能 `set_theme()`，revision 挂在 context 上而非进程级 |

**共同点**：它们都是"值语义 + 单一入口 + 可被文本断言"的东西。这也是本项目唯一被证明能长期守住的设计手段
（`test_ui_architecture` 每次构建都会跑）。

### 3.2 过度 / 投机抽象

#### A1（高）`Node` 把布局契约声明为纯虚，但全仓只有 `LayoutNode` 一个实现

```cpp
// node/node.hpp:262-274
virtual glm::vec2 measure(glm::vec2 constraints) = 0;
virtual void arrange(Rect slot) = 0;
virtual void mark_layout_dirty() = 0;
virtual void invalidate_measure() = 0;
virtual void clear_layout_dirty_recursive() = 0;
virtual Semantics semantics() const = 0;
```

- 全仓 `class ... : public Node` 只有 `LayoutNode` 一个（`grep` 命中 1）。
- 因此这 6 个纯虚函数**永远不会有第二个实现**，它们的存在只服务于一个目的：
  `for_each_child` 里可以直接 `child->measure()`。
- 代价是双向的：`children()` 只能返回 `Node*`，于是任何需要布局属性的地方都要下行：
  **14 处 `as_layout()` + 39 处 `child_at()`**，而 `LayoutNode::measure_child(Node&)` 内部就是一个
  `static_cast<LayoutNode&>`（`layout_node.cpp:82-85`）。
- 更隐蔽的代价：`Node` 自己同时是"身份/几何/树/可见性/层叠/语义钩子"的所有者，又是布局协议的声明者，
  于是 `Node` 的 17 个虚函数里有 **5 个属于布局**（`measure`/`arrange`/`mark_layout_dirty`/`invalidate_measure`/`clear_layout_dirty_recursive`）、**4 个属于语义**（`semantics*`）、1 个属于绘制（`texture_slot`）—— **抽象边界与职责边界不一致**。

**判断**：这不是"分层"，是"把转型成本从 10 个调用点搬到 14 个调用点"。
`docs/todo-ui.md` Q2 已经承认了这点（"另一个未预见的点：容器与调试面板需要约 10 处显式 `as_layout()`"），
但把它当成可接受成本。本报告认为：**要么让树的元素类型就是 `LayoutNode`（删掉 Node 的布局纯虚）**，
**要么真的引入第二类节点**（如 `DecorationNode` 只画不排）。当前状态两头不占。

#### A2（高）`ContainerNode` 是零消费者的空壳，还被测试锁死

```cpp
// node/container_node.hpp（24 行，全文）
class ContainerNode : public LayoutNode
{
public:
    void add(std::unique_ptr<Node> child) override { adopt(std::move(child)); }
    bool is_container() const { return true; }
};
```

- **0 个子类**：`Vbox`/`Hbox`/`Grid`/`Wrap`/`Panel`/`ScrollView`/`UIRoot`/`Window` 全部直接继承 `Widget`，
  并各自重写 `add()`（`linear_layout.cpp:41`、`grid.cpp:46`、`wrap.cpp:45`、`root.cpp:41`、`scroll_panel.hpp:33`）。
- **0 个调用点**：全仓没有任何地方调用 `is_container()`（`grep` 空）。
- 探针直接从编译器拿到证据：`dynamic_cast<ContainerNode*>(&vbox)` **"can never succeed"**（附录 A 编译警告）——
  `Vbox` 与 `ContainerNode` 是继承树上两个互不相干的兄弟。
- `test/test_ui_architecture.cpp:320-326` 反而用 `static_assert` 把"`ContainerNode` 挂在 `LayoutNode` 下"锁成结构契约。
  **这是最危险的一类测试：它保护的是死代码。**
- 同时 `docs/todo-ui.md` Q4 写着"`is_container()` 最终**未加到 Node**：真正需要它的地方都能直接用 `child_count()`"——
  文档的结论与代码里存在的 `is_container()` 互相矛盾。

**这就是"抽象到位没有"的直接答案：容器抽象没有落地，只落地了一个同名的类。**

#### A3（低）`Widget` 是 `LayoutNode` 的别名，但两个名字并存

`node/widget.hpp` 用别名保持 400+ 调用点不变，这个取舍本身是对的（避免破坏性迁移）。
但结果是新人必须理解"`Widget` 不是类，`Node` 不是控件"这两条反直觉事实，
且 `#include "ui/node/widget.hpp"`（16 行转发头）在 40+ 文件里出现 —— 只是别名，却保留了一个头文件层级。
可接受，但应在 `docs/ui_architecture.md` 顶部给一个 3 行"术语表"，否则每次读代码都要重新推理。

### 3.3 缺失 / 错位的抽象

#### M1（高）容器族缺共同基类，5 类"仪式"各写一遍

`LinearLayout`、`Grid`、`Wrap` 三个容器各自实现：

| 仪式 | `LinearLayout` | `Grid` | `Wrap` | 应为 |
|---|---|---|---|---|
| `add` → `adopt` | ✔ `linear_layout.cpp:41` | ✔ `grid.cpp:46` | ✔ `wrap.cpp:45` | `ContainerNode`（已存在但没用） |
| `layout()` → `arrange(global_)` | ✔ `:47` | ✔ `:51` | ✔ `:49` | 容器基类 |
| `append_to` 的 `paint_order()` 循环 | ✔ `:51-58` | ✔ `:56-63` | ✔ `:54-61` | 容器基类（或 `paint::children`） |
| `set_context` 主题注入 | ✔ `:26-30` | ✔ `:39-43` | ✔ `:37-41` | `apply_theme_metrics()` 钩子 |
| `resolve_align` | ✔ `:62-66` | ✔ `resolve_cell_align :71-75` | ✔ `:64-68` | `LayoutNode` 上一个函数 |

这不是"设计风格问题"，是**新增容器必须复制 5 段代码**（§5 成本表）。

#### M2（高）复合控件没有"chrome + content"原语

| 控件 | 内部子节点怎么托管 | 后果 |
|---|---|---|
| `Section` (`composites/section.hpp`) | `content_` 走 `adopt`（对），但 `header_` 是**裸成员**，不进树；`arrange` 里手工 `header_.set_context(context())`（:98）+ 手工摆位（:102-110）+ `append_to` 手工画（:112-116） | 所有"递归遍历"（`invalidate_measure_recursive` / `clear_layout_dirty_recursive` / `debug_recursive`）都**不会**到达 header |
| `Window` | `body_`/`footer_` 走 `adopt`，但 `Window::arrange` 用自己的 `chrome()` 手算 title/body/footer 几何（:304-345） | 窗口布局不受任何容器规则约束（已知取舍），但与 M1 的重复是同一类 |
| `ScrollPanel` | `scroll_` 是 child，`content_` 是 `scroll_` 的 content；`set_context` 手工转发（:38-42） | 想给面板加一个固定表头，只能再抄一遍 |
| `TabView` | `TabBar` 是 `children_[0]`，页面是 `children_[1..n]`，`arrange` 里按 4 种 bar 位置手算（:175-220） | 合法的特殊容器，但同样没复用 M1 |

**缺的原语**：一个 `ChromeLayout`（或 `BorderLayout`）—— "把一个装饰条 + 一个内容区按边摆好，且两者都在树里"。
今天每个复合控件都在手写它，`Section` 甚至付出了"header 不在树里"的正确性代价（§7 P1-4）。

#### M3（中）`root()` 查找复制 4 份

`Window`（`find_root_widget`，:586）、`Dropdown`（`find_root`，:294）、`MenuBar`（:259）、`DialogHost`（:248）
是**同一段代码 4 份**：

```cpp
for (Node* w = const_cast<X*>(this); w != nullptr; w = w->parent())
    if (auto* root = dynamic_cast<UIRoot*>(w)) return root;
```

`Node` 是树的元素类型，却没有 `root()` / `is_root()`；浮层宿主只能各写一遍 `dynamic_cast` 爬链。
这也是 DIP 的小破口：需要 overlay 的控件必须知道 `UIRoot` 这个具体类型。

#### M4（中）`measure()` 协议里的"固定尺寸叶子"没有一等表达

- 38 个 `measure` 实现中 **16 个 `(void)constraints`**（完全忽略约束：`Button`/`Checkbox`/`Radio`/`Slider`/`TabBar`/`TextInput`/`Table`/`TreeView`/`FileBrowser`/`SceneView`/`MenuBar`/`Dropdown`/`Tooltip`/`Scrim`/`Progress`/`UIRoot`）。
- 但只有 **3 个**声明 `fixed_size() = true`（`Window`/`Table`/`FileBrowser`）。
- 两者语义相近（"不吃父级约束"），却由两个不同机制表达，且 `fixed_size()` 只影响主轴预算与交叉轴 stretch
  （`layout_budget.hpp:63`、`linear_layout.cpp:237`），不影响 `measure`。

后果：容器无法区分"这个控件真的需要协商"和"这个控件永远报固定尺寸"，只能每次调用 `measure` 再不信它的返回值。
**建议**：把 `fixed_size()` 变成 `measure` 的前置条件（`if (fixed_size()) return clamp_size(min_size());`），
或反过来让 `(void)constraints` 的实现统一声明 `fixed_size()`；两个机制必须合并成一个。

#### M5（低）绘制部件只被一半控件采用

`paint::box` / `box_with_focus` 已被 8 个控件使用（`button`/`checkbox`/`radio`/`progress`/`text_input`/`tooltip`/`dropdown`/`tag`），
但仍有 **12 处手写 `append_rounded_rect(list, bounds, …)` + 10 处手写 `append_rounded_ring(list, bounds, …)`**
（如 `panel.hpp:49-51`、`section`/`scroll_view` 系）。更典型的是 `paint::text_size`（`painters.hpp:63-68`）：**全仓 0 个调用点**，
而 6 个文件里各自手写了"有图集就用 `atlas->measure`，否则 `estimate_text_width` 回退"的同一段逻辑。
同一个"画一个带边框的圆角矩形"存在两种写法，新控件作者只能靠读代码决定用哪种 —— 这是"抽象存在但未成为习惯"的典型状态。

## 5. 扩展性评估：加东西要付出什么

| 扩展任务 | 需要改动 | 实测/估算成本 | 主要阻力 |
|---|---|---|---|
| 新增叶子控件 | 继承 `LeafNode` + `measure` + `append_to` | **66 行**（`Tag`，M9 指标） | 低（`LeafNode` 已吸收 18 处样板） |
| 新增静态装饰叶子 | 继承 `LeafNode`，只写 `append_to` | ~20 行 | 低 |
| **新增流式容器** | 复制 R1/R2/R3/R8/R9 + 写 R4/R5 | **≈400 行**（`Grid` 86 hpp + 335 cpp），其中 ≈150 行是重复 | 高：没有容器基类可继承 |
| 新增"带装饰条 + 内容区"的复合控件 | 手工托管隐藏子节点 + 手工 `set_context` + 手工 `arrange` | `Section` = 133 行；`Window` = 679 行 | 高：没有 M2 原语 |
| 新增浮层类控件（下拉/菜单/提示） | 自行 `find_root` + `add_overlay` + 自带 scrim + 键盘导航 | `Dropdown` 386 + `MenuBar` 560 + `MenuPopup` 216 | 中高：overlay 生命周期无公共件 |
| 新增一种交互事件（如"滚轮横向"） | 改 `layout_node.hpp`（+1 虚函数）+ `UISystem::dispatch` + `event::InputEvent::Type` | 39 TU 重编；K5 预算 39/45 | 中：Q1 已否决能力接口，但预算只剩 6 位 |
| 新增主题令牌 | `Theme` 字段 + `with_density` + `style()` 映射 + `light()` | 3~4 处（`theme.hpp:123`、`theme.cpp:6-36`） | 低中：无编译期检查"新令牌是否随密度缩放" |
| 新增样式角色 | `StyleRole` + `kStyleRoleCount` + `style()` 分支 | 3 处；`static_assert` 会挡住漏改 | **低（好设计）** |
| 新增语义角色 | `WidgetRole` + `to_string` switch | 2 处 | 低 |

**扩展性结论**：

- **叶子方向是开的**：这是本轮重构最成功的部分（`LeafNode` + `Interaction` + `paint::` 三件套）。
- **容器方向是关的**：没有 `ContainerNode` 的实际继承，没有"布局算法"接口，新增容器只能复制。
- **复合方向是关的**：没有"内部 chrome 也是子节点"的机制，导致新复合控件必须手写托管，且容易漏掉递归遍历。
- **事件方向是半关的**：Q1 的否决（多继承 + `dynamic_cast`）在工程上有数据支撑，可接受；
  但可以用**非破坏性**的办法降低代价：把 16 个钩子收进一个 `EventSink` 结构体/或按 `enum class PointerPhase` 合并
  `on_mouse_down/up/click/double_click/long_press`（一次改动，虚表 -4，语义更清晰）。

## 6. 设计原则逐条对照

| 原则 | 判定 | 证据（正/反） |
|---|---|---|
| **SRP 单一职责** | ⚠️ | 反：`LayoutNode` 承担布局机制 + 交互状态 + 样式过渡 + 语义投影 + Tab 顺序 + 内容溢出诊断（10 个数据成员 / 22 虚函数）；`UIRoot` 承担自由画布布局 + overlay 宿主 + 模态栈 + 焦点钩子 + trash 队列 + 主题 context 六件事；`UISystem` 承担命中/焦点/手势/DPI/**窗口热区扫描**。正：`Interaction`/`Semantics`/`MeasureCache`/`paint::` 都是严格单责 |
| **OCP 开闭** | ⚠️ | 正：加样式角色/主题令牌不改控件（`Theme::style` 策略表）；加叶子控件不改基类框架。反：加事件要改基类；加容器要复制实现；`WidgetRole` 新增要改 `to_string` 的 switch |

| **DIP 依赖倒置** | ⚠️ | 反：`Node::context()` 走父链 + `ui::theme()` / `active_font_atlas()` 全局回退（5 处 `active_font_atlas()`），是隐式 service locator；`ui_system.cpp:3` 直接 `#include "ui/composites/window.hpp"` 并为 `Window` 写专用热区扫描（`find_resize_target`/`update_resize_cursor`）—— 调度层依赖具体复合控件。正：`UIContext` 注入 + 焦点钩子注入（`set_focus_hooks`）避免了 `UIRoot → UISystem` 的反向依赖；`ScrollMode`/`GlyphLoader` 是策略式抽象 |
| **DRY** | ⚠️ | 见 §4：主轴/缓存/语义/绘制已收敛（真 DRY）；容器仪式/`find_root`/`set_enabled` 覆写/文本测宽仍是重复（假 DRY） |
| **KISS** | ⚠️ | 正：`LayoutSpec`/`Semantics`/`Interaction` 都是"数据 + 转发"，没有额外间接层。反：`MeasureKey` 一个结构体塞 8 个字段（其中 6 个只有 `Label` 用），所有控件都付 56 B 并施加"派生输入"心智负担；`layout_spec()` 的"读-改-写"在 8 个 setter 里各复制 9 个字段并 `mark_layout_dirty()` |
| **YAGNI** | ❌ | `ContainerNode`（0 子类 / 0 调用）、`is_container()`（0 调用）、`Node` 上的布局纯虚（1 个实现）三处都是"为想象中的第二实现付费" |
| **组合优于继承** | ⚠️ | 正：4 个部件 + `paint::` + `UISystem::Target` 都是组合/值语义。反：`LayoutNode` 把布局、交互、样式三种能力串在一条继承链上；`LeafNode`/`ContainerNode` 想按"能力"分叉，但 `ContainerNode` 没被使用 |

## 7. 实测问题

### P0-1（已复现）`Window::destroy()` 在未注册回调时**立即析构自身**，注释却承诺"延迟到下一次 layout"

```cpp
// window.hpp:184-195
void destroy()
{
    release_modal();
    if (on_destroy_) { on_destroy_(); }
    else if (auto* root = find_root_widget()) {
        // 未注册回调：从 root 的子项中延迟移除（不再退化为"隐藏但留在树上"）。
        root->remove(this);
    } else { set_visible(false); }
}
```

而 `UIRoot::remove()`（`root.cpp:49-58`）虽然注释写着"先移入 `trash_` 延后销毁"，
实际调用的是 `remove_children_if(...)` —— **立刻 erase 掉 `unique_ptr`**：

```cpp
// root.cpp:53-57
// 先移入 trash_ 延后销毁（事件回调里可能还在使用该控件）
remove_children_if([child](const std::unique_ptr<Node>& c) { return c.get() == child; });
```

探针（附录 A `[2]`）：

```
[2] before destroy: dtors=0 children=1
[2] after  destroy: dtors=1 children=0     ← 在 destroy() 尚未返回时对象已被 delete
```

后果：`destroy()` 返回后继续执行该对象成员函数 = **use-after-free**。
`window.hpp:315` 的注释（"`UIRoot` 已用 `trash_` 延迟实际析构"）与此直接矛盾。
目前 `src/` 与测试里所有 `destroy()` 路径都先注册了 `on_destroy_`（`test/test_ui_window.cpp:140,293,353`），
所以这是**未爆的雷**，不是现行崩溃。

同一行代码还有第二个缺陷（探针 `[3]`）：

```
[3] nested window: dtors=1 window.visible=1   ← destroy() 完全没生效
```

`UIRoot::remove()` 只扫 **root 的直接子项**。窗口若被放进 `Vbox`/`Panel`（`Window` 的注释只说"通常放 root 下"），
`destroy()` 静默变成 no-op，窗口仍然可见、仍在树上。

**修法**（二选一，都是小改）：

1. 让 `remove()` 真的走 `trash_`（顺带修 `pop_modal` 里同样直接 erase scrim 的两处），并在 `layout()` 里 `purge_trash()`（现有代码已具备）；
2. 或让 `Window::destroy()` 只做 `set_visible(false)` + `pending_destroy_ = true`，把"从父节点摘除"交给下一次 layout —— 这正是注释描述的行为。

### P0-2（已复现）`Grid` 的 `measure` 与 `arrange` 用**不同约束**测量同一子项 → 缓存永不命中，每轮测两次

```cpp
// grid.cpp:212（measure）   cell_w + 有界内高
const glm::vec2 cs = Widget::measure_child(*child, {cell_w, inner_h});
// grid.cpp:266（arrange）   cell_w + 无界高
glm::vec2 cs = Widget::measure_child(*child, {cell_w, kUnbounded});
```

`MeasureCache` 的键是 `(constraints, epoch)`（`measure_cache.hpp:34-42`），约束不同必然 miss。探针：

```
[1] LinearLayout(Vbox) measures = 1     ← 命中（好）
[1] Wrap measures = 1                   ← 命中（好）
[1] Grid measures = 2                   ← measure + arrange 各测一次
```

后果：`Grid` 子项（文本类控件 = 两次全量字形遍历）每轮布局被测量两次；
嵌套 Grid 时按层数翻倍。这不是性能微优化问题，而是**"唯一入口 + 唯一缓存"的契约在 Grid 里被自己破坏**。

**修法**：`arrange` 复用 `measure` 的同一约束（或反过来），并在 `grid.cpp` 里加一条"measure/arrange 约束必须一致"的注释；
更根本的是把"采集子项规格"抽成一份（R4），约束自然只有一处。

### P1-3（已复现）容器 `measure()` 可以返回大于 `constraints` 的尺寸

```cpp
// linear_layout.cpp:126-130
const glm::vec2 result = clamp_size(extent + glm::vec2{pad_l + pad_r, pad_t + pad_b});
store_measure(constraints, result);
```

`clamp_size` 只夹 min/max，不夹 constraints。探针：

```
[5] vbox(wide child).measure = 300.0 x 10.0  (constraints 200 x 100, <= ? NO)
```

而 `docs/ui_architecture.md` 的核心契约写的是"返回值宽度不得超过它（`min_size` 强制除外）"。
现有 `test_ui_layout_contract` 只用一个 `Label` 子项验证，恰好没触发这条。

**修法**：`measure` 末尾对主轴做 `std::min(size, constraints)`（`Wrap` 已经这么做：`wrap.cpp:146-147`），
或把契约改成"允许溢出，由父级 clip/scroll 决定"—— 两者可以，但必须只选一个并写进契约测试。

### P1-4（已复现）`Section` 绕过 `measure_child` 与测量缓存，且 `header_` 不在树里

```cpp
// section.hpp:80-88：直接 content_->measure(...)，不经 LayoutNode::measure_child
const glm::vec2 inner = content_->measure({avail_w, kUnbounded});
```

- `Section::measure` 没有 `measure_cache_hit/store_measure` → 自身缓存永远不命中（探针 `[6]`：连续两次 `measure`，内容被测量两次）。
- 直调 `content_->measure` 意味着子项的 `margin` / `pct` / `fill` / `aspect` / 缓存全部失效（`measure_child` 才是唯一入口，UI-31 契约）。
- `header_` 是裸成员（`section.hpp:124`），不在 `children_`，因此 `invalidate_measure_recursive` / `clear_layout_dirty_recursive` /
  `debug_recursive` 都不会到达它；`arrange` 里手工 `header_.set_context(context())`（:98）就是在补偿这一点。
- 同类"直接 measure 子项"的还有 `Window::layout`（`footer_->measure`，:325）与 `ScrollView::update_metrics`（:46/:62）——
  后两者有合理理由（内容尺寸 vs 布局协商），但契约文本目前把"宿主一律走 measure_child"写死了，代码实际有 5 处例外。

**修法**：`Section` 改用 `measure_child` + 缓存；`header_` 要么 `adopt`（并让 `children()` 顺序为 header→content），
要么在 `Section` 上显式覆写递归失效。前者更好，但这需要 M2 的"chrome + content"原语，否则只是把手工代码搬个位置。

### P1-5（已核实）7 个控件覆写的 `set_enabled()` 与基类**逐字相同**

```cpp
// layout_node.hpp:50-54（基类）
virtual void set_enabled(bool enabled) { input.enabled = enabled; mark_layout_dirty(); }
// button.hpp:31 / checkbox.hpp:30 / color_input.hpp:45 / drag_float.hpp:41 /
// radio.hpp:41 / slider.hpp:45 / text_input.hpp:43 —— 同样的 body
void set_enabled(bool enabled) override { input.enabled = enabled; mark_layout_dirty(); }
```

这是 R2"状态收敛"的**残留**：字段搬进 `Interaction` 后，这些覆写已无作用，只增加虚调用与维护面。
同类还有 8 处 `bool enabled() const { return is_enabled(); }`。
删除是零风险的（基类行为完全一致），属"一次提交可清干净"的技术债。

### P1-6（已核实）ContainerNode / is_container 是死抽象，但被架构测试锁住

见 §3.2-A2。补充：`is_container()` 在 `docs/todo-ui.md` Q4 里被明确否决（"加一个非虚查询但语义歧义不划算"），
代码里却存在这个方法，且 `test_ui_architecture.cpp:326` 断言它存在。
**测试正在保护一个文档说不该存在、代码里也没人用的东西。**

### P2-7（已核实）`Interaction` 的"单一所有者"在 4 处被绕过

```cpp
// panel.hpp:46       —— enabled 硬编码 true，禁用面板仍显示 hover
Interaction{true, is_hovered(), false}.state()
// splitter.hpp:162   —— 同上，且忽略 focused
Interaction{true, is_hovered(), input.dragging}.state()
// dropdown.hpp:162/171 —— 手工拼 3/6 个布尔位置参数
```

位置聚合初始化（6 个 `bool` 挨着写）还带来可读性风险：`{input.enabled, active, false}` 第三位是 `pressed`。
建议给 `Interaction` 加一个 `with(overrides)` 或直接提供 `state_of(enabled, hovered, pressed, checked)` 自由函数。

### P2-8（已核实）"不吃约束"有两种表达机制，且多数实现没声明

38 个 `measure` 实现里 16 个 `(void)constraints`，只有 3 个声明 `fixed_size()`。
`fixed_size()` 只影响主轴预算/交叉轴 stretch（`layout_budget.hpp:63`、`linear_layout.cpp:237`），并不影响 `measure` 调用本身。
结果是容器需要**同时**读 `fixed_size()` 和"信任 measure 的返回值"，两套语义并存。

### P2-9（已核实）容器的 `layout()` 钩子在 `src/` 里没有调用者

`LinearLayout::layout`/`Grid::layout`/`Wrap::layout`（`arrange(global_)` 重排）只在 `test/test_ui_layout_probe.cpp:279` 被调用；
生产路径走 `UIRoot::layout()`。同时 `Window::layout()` 被用作 `pending_destroy_` 钩子（`window.hpp:315-320`），
两者语义完全不同却共用一个虚函数名。**建议**：容器删除 `layout()` 覆写；`Window` 的延迟销毁改成 `on_layout_pass()` 之类的专名。
