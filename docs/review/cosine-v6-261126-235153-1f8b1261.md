## 0. 结论摘要

`src/`（125 文件 / 22,876 行）不是「教科书式套模式」的代码库，而是**少数几个模式被彻底贯彻、
其余位置用更轻的手段替代**：模式密度最高的是 `Composite`（42 个 `Widget` 子类共用一条树遍历路径）、
`Template Method`（`Widget` 的 measure/arrange/append_to 三件套）、`Command`（11 个命令类 + 撤销栈）、
`Strategy`（角色表 `theme.style(role, state)` 取代控件内分支）。

| 分类 | 模式 | 落点数 | 结论 |
|---|---|---|---|
| 创建型 | 静态工厂 / 命名构造 | 7 | 恰当：`Theme::dark()/light()`、`with_*()` |
| 创建型 | Prototype（复制-改字段） | 5 | 恰当但**手写五份**，新字段易漏 |

| 结构型 | **Composite** | 4 | 核心模式：控件树、Drawable、CompoundCommand、Overlays |

**三个主要风险**（详见 §8）：

1. **宽接口**：`Widget` 有 54 个虚成员，42 个子类全量继承 —— 加一种交互就要动基类（与 UI-37「setter 17→10」同源）。
2. **每控件 1,688 字节过渡缓存**（实测 `sizeof(StyleTransition)`），懒分配但一旦交互就长期持有。
3. **Observer 三套并存**（`std::function` 回调、focus hooks、虚钩子），语义不一致（有的返回 `bool` 表示消费，有的 `void`）。

## 2. 结构型模式

### 2.1 Composite —— 整个 UI 层的骨架

**落点**：`src/ui/widget.hpp:98-105`

```cpp
virtual void add(std::unique_ptr<Widget> child) { ... }
virtual const std::vector<std::unique_ptr<Widget>>& children() const { return children_; }
virtual const std::vector<std::unique_ptr<Widget>>& overlays() const { ... }
```

42 个子类（`src/ui/{core,containers,composites,views}` + `UIRoot`）全部同构，于是这些遍历
**只写一次**、对整棵树生效：

| 遍历 | 位置 | 作用 |
|---|---|---|
| `measure/arrange` | `widget.hpp:223-224`（纯虚）+ `root.cpp:119-175` | 两趟布局 |
| `append_to` | `graphics/drawable.hpp:181-186`（基类纯虚） | 一次收集绘制指令 |
| `mark_layout_dirty` | `widget.hpp:498-506` | 脏标记沿 parent 上溯 |
| `invalidate_measure_recursive` | `widget.hpp:522-528` | 主题/密度变更全树失效 |
| `clear_layout_dirty_recursive` | `widget.hpp:512-519` | 每轮布局收尾 |
| `collect_hit_path` | `ui_system.cpp:19-38` | 命中测试（z 降序） |
| `invalidate_measure` / `layer_paint_order` | `widget.hpp` | 缓存与绘制顺序 |

**评价**：这是全仓最一致的模式，收益明确——加一个新控件（如 `PreviewRuler`）只需实现
`measure/arrange/append_to` 三个方法就自动获得布局、裁剪、命中、主题切换、调试面板支持。

**代价**：`children_` 与 `overlays()` 是**双容器**，每个遍历点都要写两遍（`mark_layout_dirty`
不覆盖 overlays，`clear_layout_dirty_recursive` / `invalidate_measure_recursive` /
`layer_paint_order` 则都要两份）。UI-34 的 `clear_layout_dirty` 只清自身、UI-45 修出"未递归"缺陷，
正是这个双容器结构造成的——**漏一处就是 bug，且不会被编译器发现**。

### 2.2 Composite 的另外三处

| 落点 | 组合单位 | 说明 |
|---|---|---|
| `graphics/drawable.hpp:181` | `Drawable::append_to(DrawList&)` | `Rectangle/Line/Triangle/Sprite` 都是叶子；`Widget` 也是 `Drawable`，于是"控件画自己"与"图元画自己"共用同一入口 |
| `anim/command.hpp:256` | `CompoundCommand` | 宏命令：`apply` 正序、`revert` 逆序（`command.cpp:220-229`），多选拖动一次撤销 |
| `ui/composites/menu_bar.hpp:716` | `menu_items(bar, index)` | 菜单/子菜单嵌套同构，按索引路径寻址 |

### 2.3 Adapter —— 边界隔离

| 落点 | 被适配者 | 隔离收益 |
|---|---|---|
| `backend/window.hpp:21` | GLFW | UI 层不出现 GLFW 常量；系统光标用 `Window::Cursor` 枚举表达 |
| `graphics/font_face.hpp:12` | FreeType | `FT_Library`/`FT_Face` 完全封装，对外只暴露 `add_glyph(FontAtlas&, ...)` |
| `ui/ui_system.cpp:178` | `event::InputEvent` | 把扁平事件对象翻译成控件虚钩子（`on_mouse_down` 等） |

**评价**：三处都是"一个头文件挡住一个 C 依赖"的经典 Adapter，没有多余抽象层（没有为了适配而适配）。

### 2.4 Facade / 组合根

`src/xel_application.hpp:11` 的 `Application` 是显式组合根：`window_` / `vulkan_context_` /
`swap_chain_` / `renderer_` / `uisys` 五个成员，构造顺序即依赖顺序，注释也写明"Editor 在
Application 之后构造，析构顺序相反"。`UISystem` 是 UI 侧的 Facade（`tick/dispatch/set_focus`）。

**评价**：组合根公开成员（不是 private），这是有意的——两个示例程序与测试都直接摸 `app.uisys`，
省掉 20 行 getter。作为应用层入口可接受；若将来做库分发，这会是第一个要封装的地方。

### 2.5 Bridge —— 两处真正的桥

| 抽象侧 | 实现侧 | 分界 |
|---|---|---|
| `Drawable`（画什么） | `DrawList`（怎么攒批）/ `Renderer`（怎么进 GPU） | `append_to(DrawList&)` 是唯一接触点；`DrawList` 负责裁剪栈、透明度栈、纹理槽、批切换（`drawable.hpp:56-176`） |
| `Theme`（样式数据） | `Theme::style(role, state)`（解析策略） | 控件只说"我是 Track 的 Hovered"，不碰具体色值（`style.hpp:69-210`） |

第二处是本仓最有价值的解耦：UI-39/UI-40 把"控件内手写颜色分支"降到 0，靠的就是这条桥。

### 2.6 Decorator 的实际形态：叠层而非包装链

本仓没有 `class Border : public Widget { Widget* inner; }` 这种包装链（`Panel : public Vbox`
是继承扩展而非包装）。真正的"装饰"通过 **overlay 挂件**实现：

- `widget.hpp:105` `overlays()`：控件自带的浮层（Tooltip、下拉列表、菜单弹窗）
- `ui/core/scrim.hpp:21` `Scrim`：模态遮罩，由 `UIRoot::push_modal` 自动插入（`root.cpp:181-193`）
- `ui/composites/menu_bar.hpp` `MenuScrim` / `MenuPopup`

**评价**：叠层式装饰比包装链更适合 UI（需要 z 序与裁剪域隔离），但代价是"浮层不是子节点"——
布局不参与、命中要单独走 `layer_paint_order()`，这也是 §2.1 双容器代价的另一面。

### 2.7 Proxy —— 句柄与生命周期令牌

`ui/ui_system.hpp:68-86` 的 `Target` 是本仓最精巧的一段：

```cpp
struct Target {
    Widget* widget = nullptr;
    std::weak_ptr<const bool> token;      // alive_token()
    bool valid() const { return widget != nullptr && !token.expired(); }
    operator Widget*() const { return widget; }   // 隐式转换，调用点零改动
};
```

`hovered_ / pressed_ / focused_` 三处都用它。控件被 `clear_children()` / `set_content()`
直接销毁时令牌过期，指针即使非空也不会被解引用。这是**代理 + 观察者**的混合：代理负责
"看着像指针"，令牌负责"知道对象死了"。

`cosine/texture_cache.hpp:16` 的句柄约定（返回值 = 图片槽索引 + 1，0 表示未绑定）也是同族
思路：用值语义句柄替代裸指针，槽位由 `Renderer` 集中管理。

### 2.8 Flyweight —— 共享的开销大的部分

| 共享对象 | 大小/数量 | 共享方式 |
|---|---|---|
| `Theme` | **600 B**（实测） | 整棵树持有 `UIContext` 里的一份拷贝，revsion 变更才重建 |
| 字形图集 | 一张 Vulkan 纹理 + `Glyph` 表 | `FontAtlas` 按 (codepoint, pixel_size) 缓存 |
| 纹理槽 | 16 槽（1 白 + 1 图集 + 14 图片） | `graphics::image_slot()` 映射；超限回退色块 |

**反例（值得关注）**：`StyleTransition` 是**每控件独有**的，实测 `sizeof = 1,688 B`（12 槽 × 140 B）。
`Widget::visual_style()` 首次调用就 `make_unique<StyleTransition>()`（`widget.cpp:124`），
且此后不清空。交互过的控件（hover 一次即可）都会长期持有 1.7 KB：

```
1000 个交互过的控件 ≈ 1.7 MB，10000 个 ≈ 17 MB
```

真正的 Flyweight 做法是把 `(role, state) → 插值` 表按主题共享、控件只存 4 字节索引；或者
把 `from/to` 换成"起始时间 + 起止槽号"。当前实现用内存换实现简单，属于**有意识的取舍**，
但没有任何注释记录这个取舍，容易被误认为零成本。

## 3. 行为型模式

### 3.1 Template Method —— 布局与绘制的固定骨架

| 骨架（非虚/基类实现） | 可覆写步骤 | 位置 |
|---|---|---|
| `Widget::update(dt)` | `on_update(dt)` | `widget.hpp:588-592`（NVI：非虚包虚） |
| `Widget::measure_child()` / `UIRoot::layout_child()` | `measure()` / `arrange()` | `root.cpp:119-139`、`widget.hpp:223-224` |
| `Widget::advance_transition(dt)` | —（固定） | `widget.cpp:170` |
| `ListView::append_rows()` / `draw_scrollbar()` | `item_count()` / `draw_row()` / `viewport_height()` | `list_view.hpp:51-58, 150, 179` |

`ListView` 是全仓抽得最干净的一处 Template Method：

```cpp
// list_view.hpp:51-58 —— 三个纯虚是全部"变量部分"
virtual std::size_t item_count() const = 0;
virtual void draw_row(DrawList&, std::size_t index, Rect row, bool selected) = 0;
virtual float viewport_height() const { return global_.size.y; }
```

`Table` 与 `TreeView`（`table.hpp:30`、`tree_view.hpp:31`）只实现这三个方法，就自动获得：
像素对齐的行循环、可见窗口裁剪、滚动条绘制与拖动、增量滚动状态。**新增一个列表类视图
不需要再写一遍滚动条**（UI-46 修滚动条配色时正是只改了这一处，三个视图一起生效）。

`Widget::update` 的 NVI 写法也值得记录：

```cpp
void update(float dt) { advance_transition(dt); on_update(dt); }   // 非虚
```

注释直说理由："非虚，避免派生类覆写时漏调基类"。这与本仓两次真实缺陷（`clear_layout_dirty`
未递归、`mark_layout_dirty` 早退漏位）是同一类教训——**能封成非虚基类实现就不要交给 42 个子类自觉**。

### 3.2 Strategy —— 用表和函数替代继承

| 策略 | 载体 | 替代了什么 |
|---|---|---|
| 角色样式解析 | `Theme::style(StyleRole, ControlState)`（`style.hpp:69-210`） | 控件内的 `if (hovered) ... else if (disabled) ...` 颜色分支（UI-40 已降到 0） |
| 主轴尺寸分配 | `resolve_main_axis(...)`（`layout_budget.hpp:44`） | `Vbox`/`Hbox` 各自手写的 flex 分配（UI-32 收敛） |
| 流式方向 | `LinearLayout(Axis)`（`linear_layout.hpp:19`）+ `Vbox`/`Hbox` 薄封装 | 两份几乎相同的 arrange（UI-36） |
| 字号档位 | `Theme::text_size_of(TextSize)`（`theme.hpp:180`） | 各控件直读 `small_text_size`（UI-41 归零） |
| 字形加载 | `FontAtlas::set_glyph_loader(GlyphLoader)`（`font_atlas.hpp:47`） | 图集不依赖 FreeType（依赖注入） |
| 滚动行为 | `ScrollMode`（`scroll_mode.hpp`）+ `ScrollState` | `Table`/`ScrollView`/`TextInput` 三份各自实现（已收敛） |
| 焦点/密度/圆角策略 | `Theme::with_focus_policy/with_density/with_rounding` | 控件内 `if (theme.xxx)` 分支 |

**评价**：本仓的 Strategy 几乎全部是**函数/枚举/表驱动**，而不是"抽象基类 + 派生策略类"。
这是合理选择：策略维度是数据（颜色、字号、方向），不是行为算法族，引入类层次只会增加间接层。
代价是策略组合靠调用方自觉（`Theme::with_*` 五个方法必须按顺序叠加，见 §8-R5）。

### 3.3 Command —— 唯一带撤销的应用级模式

**落点**：`src/anim/command.hpp`

```
Command (19)  ← 抽象：name/apply/revert
CommandStack (29)  ← 撤销栈：push 时 apply，undo 调 revert，redo 再 apply；上限 256
11 个派生：10 个原子命令（SetProperty / SetPropertyValue / SetNodeField / AddNode /
           RemoveNode / SetNodeColor / MoveKey / SetKeyEasing / AddKey / RemoveKey）
         + 1 个宏命令 CompoundCommand
```

三处细节做对了：

1. **`push` 即 `apply`**（`command.cpp:9-16`）：调用方不需要先执行再入栈，避免"执行了但没入栈"的状态不一致。
2. **`push` 清空 redo 分支**（`command.cpp:14`）：撤销后再编辑，重做历史正确失效。
3. **`revert` 逆序**（`command.cpp:225-229`）：宏命令的回滚顺序正确。

**约定靠注释而非类型**：`apply`/`revert` 必须幂等成对（`command.hpp:13-15` 有明确约定），但
编译期无法保证。`CompoundCommand::apply` 若第 3 条失败，前 2 条已生效且无补偿——目前所有命令
都是"改字段"，不会失败，所以不是现实缺陷，但扩张时（如带 IO 的命令）会暴露。

### 3.4 Memento —— 四份"状态快照"，只有两处是真快照

| 落点 | 快照内容 | 恢复方式 |
|---|---|---|
| `anim/serialize.hpp:20-28` | 整个 `Project` → 字节流 | `deserialize` 重建（含版本 tag，见 `serialize.cpp` §4） |
| `anim/command.hpp:49-51` | `SetPropertyCommand` 首次 `apply` 时记录 `before` | `revert` 写回 |
| `root.cpp:181-193` | `push_modal` 记录打开前的焦点 | `pop_modal` 恢复焦点与 z 序 |
| `widget_style.hpp:16-30` | `StyleSlot{from, to, progress}` | 不是快照，是插值状态（见 §3.5） |

前两处是标准 Memento（把对象状态提出来存外部、不影响封装）；第三处是**焦点栈**，
功效类似但语义更窄。序列化那份还额外承担"格式契约"角色（`value_tag` 与 `docs/project_format.md §4`
对齐、显式不用 `variant::index()`），属于 Memento + 显式协议的组合。

### 3.5 State —— 三处显式状态机

1. **样式过渡**（`widget_style.hpp:37-52`）：12 个 `StyleSlot`，每槽 `{state, from, to, progress}`。
   状态变化时 `from = lerp(from, to, progress)`、`to = target`、`progress = 0`，于是"中途反向
   （hover→normal→hover）不跳变"（`widget.cpp:139-145`）。这是**每槽独立的小状态机**。
   本仓 UI-46 的"滚动条滑块消失"就是这套状态机的边界条件被踩到：槽按 role 索引、不区分 state，
   同帧双状态互相覆盖 → 两处都停在中间色。修复是拆角色（`Track` + `Thumb`）而不是改状态机，
   说明状态机本身正确、**契约（一帧一角色一状态）需要显式化**。
2. **滚动**（`scroll_state.hpp:12`）：`value / target / viewport / content / smoothing` 五项，
   `jump_to` 立即到位、`set_range` 重新夹取、平滑逼近。把三处重复实现收敛到一处。
3. **播放/展开**：`Timeline` 的 playing/time、`Dropdown`/`MenuBar` 的展开态、`TabView` 的当前页
   —— 都是简单布尔/枚举，没有独立状态类。

### 3.6 Observer —— 三套机制并存

| 机制 | 落点 | 语义 |
|---|---|---|
| `std::function` 回调 | 93 处（`Player::add_event` `player.hpp:18, 42`、`FontAtlas::GlyphLoader`、各 `on_click`/`on_select`） | 单向通知，无返回值 |
| focus hooks | `UIRoot::set_focus_hooks(getter, setter)`（`root.hpp:37-40`） | 双向注入，避免 `UIRoot` 依赖 `UISystem` |
| 控件虚钩子 | `widget.hpp:469-487`（`on_mouse_down` 等） | **有返回值**：`bool` 表示"已消费" |

**评价**：没有统一事件总线是有意为之——UI 不需要跨层广播，虚钩子 + `bool` 消费标志更直接
（省掉订阅/退订生命周期管理，也避免悬垂回调）。但三套并存带来一个真实成本：**消费语义不统一**。
`on_mouse_down` 返回 `bool`、`on_hover` 返回 `void`、`on_focus_gained` 返回 `void`，
调用方（`ui_system.cpp` 的 dispatch 分支）必须逐个记住哪一类可以"吃掉"事件。

focus hooks 那处值得一提：`UIRoot` 需要知道"当前焦点是谁"才能做模态焦点快照，但它不该依赖
`UISystem`（层级倒置），于是把 getter/setter 作为函数注入。这是**依赖注入的最小形态**，
比引入接口类轻得多。

### 3.7 Chain of Responsibility —— 命中链

`ui_system.cpp:19-38` 的 `collect_hit_path` 沿树下降并累积路径：

```cpp
path.push_back(widget);
for (auto it = order.rbegin(); it != order.rend(); ++it)
    if (collect_hit_path(*it, pos, path)) return true;   // 大的先命中
if (widget->hit_testable() && widget->global_bounds().contains(pos)) return true;
path.pop_back();
```

返回的 `path` 顺序是"根 → 最深命中者"，dispatch 时从最深处开始尝试，`event.handled` 决定是否
继续冒泡（`event.hpp:30-31` 的 `consume()`）。这是**链 + 事件标志**的组合，而非经典"每个处理者
持有 next 指针"。

**评价**：比显式链更适合 UI（层级由树天然给出）；代价是 `path` 每帧分配一个 `std::vector`
——鼠标移动频率高，这是一处可优化点（可复用成员缓冲区）。

### 3.8 Mediator —— Editor 是中心，也是风险集中点

`src/cosine/editor.cpp`（976 行）同时持有：

```cpp
std::unique_ptr<anim::Player> player_;      // editor.hpp:107
TextureCache texture_cache_;               // editor.hpp:110
anim::CommandStack stack_{256};            // editor.hpp:111
std::unique_ptr<ResourceBrowser> resource_browser_;   // :140
std::unique_ptr<SettingsWindow> settings_window_;     // :142
std::unique_ptr<DebugWindow> debug_window_;           // :144
```

它把"面板操作 → 命令栈 → 播放器 → 场景 → 预览"串起来，是典型的 Mediator：让 `Table`/`Slider`/
`DebugWindow` 之间不互相认识，全部只跟 `Editor` 说话。

**评价**：中介本身必要，问题在**规模**——它同时承担菜单命令分发、属性面板构建、资源浏览器装配、
密度/主题联动、快捷键、截图导出。这已经从"中介"滑向"上帝对象"（与 `backend #1` 对 `Renderer`
的判断同类）。1024 行的文件里，可分离的至少有：命令分发、面板装配、密度/主题应用三块。

### 3.9 Visitor —— 两处弱形态

1. **`std::visit` over `PropertyValue`**（`serialize.cpp:84`）：`std::variant<float, vec2, vec3,
   vec4, bool, string, uint32>` 上的 `if constexpr` 分派，是 Visitor 的编译期形态。注释说明
   "不使用 `variant::index()`"，因为 tag 是**格式契约**的一部分，不能随类型顺序漂移。
2. **调试面板**（`debug_window.cpp:42/81/96/403`）：递归遍历控件树读取几何与状态。这是"遍历型
   Visitor"，但每个控件没有 `accept(visitor)`，而是调试面板直接读 `Widget` 的公开状态。

**评价**：第 2 处是**有意不做**经典 Visitor——42 个控件的 `accept` 会让基类再胖一圈，而调试面板
需要的信息已经在 `Widget` 公开 API 上（`children()/global_bounds()/layout_dirty()` 等）。
代价是调试面板只能看到"通用状态"，看不到控件特有字段（如 `Slider` 的当前值），
`DebugWindow` 为此加了逐类型的 `if` 分支（`debug_window.cpp:403` 附近）——这是"不做 Visitor"的
真实成本，属于可接受的小额技术债。

## 4. 创建型模式

### 4.1 静态工厂 + 命名构造

```cpp
static Theme dark() { return Theme{}; }   // theme.hpp:201
static Theme light();                     // theme.hpp:202
```

`Theme` 的默认构造值就是深色，所以 `dark()` 是零成本的命名构造；`light()` 在 `theme.cpp` 里
逐字段覆盖。这类"静态工厂"的价值是**给两份数据起名字**，避免散落的 `Theme{}` / `Theme::light()`
之外再来一个 `bool dark` 参数。

`UISystem` 的两个构造函数（有窗口 / 纯逻辑测试用 `unique_ptr<UIRoot>`，`ui_system.hpp:19-21`）
也是同族：用重载表达"两种装配方式"，而不是在构造函数里塞 `if (window != nullptr)`。

### 4.2 Prototype（复制-改字段）—— 手写五份

```cpp
Theme with_density(Density target) const;      // theme.hpp:190
Theme with_rounding(bool rounded) const;       // :193
Theme with_focus_policy(FocusPolicy) const;    // :195
Theme with_transition_ms(float ms) const;      // :197
Theme with_radius_scale(float scale) const;    // :199
```

每个实现都是"整体拷贝 + 改若干字段 + 返回"。这是不可变风格的 Prototype：调用方永远拿到新值，
共享的旧值不受影响，非常适合"主题叠加"（`Theme::dark().with_density(Compact).with_rounding(false)`）。

**风险**：字段列表在五处重复，新增主题字段时**必须逐个检查哪个 `with_*` 该动它**。
历史缺陷正是这一类——`Editor::kDensity` 表只缩放了一部分字段（字号/控件高度），
导致设置窗口的 checkbox/scrollbar/radius 不跟随（T38/UI-43 才收敛到唯一机制 `with_density`）。
README 里没有"新增主题字段要检查清单"，这是可预防的。

### 4.3 Builder

| 落点 | 构建产物 | 手法 |
|---|---|---|
| `graphics/font_atlas_builder.hpp` | 字体图集（字形 + 度量 + 纹理像素） | `FontAtlasBuildOptions` + `FontCandidate` 列表，分步装配 |
| `graphics/drawable.hpp:56-176` `DrawList` | GPU 批次（`DrawBatch`） | 即时模式：`push_clip/pop_clip`、`push_opacity/pop_opacity`、`set_texture_slot` 边画边定批 |

`DrawList` 严格说是**状态栈 + 延迟批提交**，但它承担了 Builder 的角色：调用方只描述图元，
`DrawList` 决定何时开新批（`needs_new_batch_`）。裁剪/透明度用**成对括号**表达
（`push_clip` ↔ `pop_clip`），而不是 RAII —— 这是本仓少数**没用 RAII 的地方**，见 §8-R6。

### 4.4 弱单例 / 进程级服务

```cpp
const PropertyRegistry& builtin_properties();   // property.hpp:67
inline const Theme& theme() { ... }             // theme.hpp:227（只读回退）
```

两处都是"进程内唯一、构造后只读"，没有 `instance()` 式可变单例。`ui::theme()` 是 UI-42 之后的
**降级产物**：主题写入口已收窄到 `UIContext::set_theme()`（推进 per-context revision），
全局那份只作为"无 context 的裸控件"的只读回退保留。这是正确方向——单例的可变部分被消除，
只留下不可变默认值。

### 4.5 对象池

| 池 | 容量 | 策略 |
|---|---|---|
| `Renderer` 图片槽 | 14 张 | `graphics::image_slot(index)` 映射到纹理槽 2..15；超限回退到色块 |
| `TextureCache` | 同上 | 路径 → `Entry{slot, w, h}`，`load()` 已缓存则不重复上传（`texture_cache.hpp:16-36`） |
| `FontAtlas` 图集空间 | 一张纹理 | `add_glyph` 失败标记"图集满"（与"字符不存在"区分，`font_atlas.hpp:88-89`） |

三处都用"**句柄 + 容量上限 + 明确回退**"的三段式，没有动态扩容——上限是渲染管线的硬约束
（16 个描述符槽），提前暴露比运行期失败更好。

## 5. C++ 惯用法（承担模式职责，但不属于 GoF）

| 惯用法 | 落点 | 承担的职责 |
|---|---|---|
| **RAII** | `LayoutPassScope`（`widget.hpp:35-43`，`widget.cpp:42`） | 标记"正在布局"，使 arrange 内的几何写入不再触发重排；析构自动恢复，异常安全 |
| **RAII** | Vulkan 资源（`backend/vulkan/*`） | 句柄成对释放，`~Renderer`/`~SwapChain` 负责销毁 |
| **NVI** | `Widget::update`（非虚）+ `on_update`（虚） | 强制派生类复用"推进过渡"这一步 |
| **Type Erasure** | `std::function` 93 处 | 回调/事件/策略注入，全部免去接口类 |
| **非拷贝 + 令牌** | `Widget(const Widget&) = delete` + `alive_token()`（`ui_system.hpp:72`） | 树形所有权 + 悬垂检测 |
| **不可变值 + 派生方法** | `Theme::with_*`、`Align::center()` 等 12 个命名构造（`align.hpp:21-33`） | 表达"配置组合"而不引入 Builder 类 |
| **表驱动分派** | `Theme::style()` 内 `switch (role)` × `switch (state)` | 12×5 的外观矩阵，新增角色只加一个 `case` + `static_assert` 兜底 |
| **编译期契约** | `kStyleRoleCount` + `static_assert(Thumb + 1 == count)`（`widget_style.hpp:13, 42-43`） | 枚举与数组容量不同步时编译失败 |
| **未使用** | CRTP、PImpl、多继承接口 | 本仓刻意不用：编译单元已拆成 OBJECT 库（`docs/ci.md` 有记录），PImpl 收益不足以抵消间接层 |

`LayoutPassScope` 值得单独说：它解决的是**重入**问题（布局过程中写几何 → 又请求布局 → 无限递归）。
用 RAII 而不是布尔成员，是因为"异常安全 + 作用域精确"两件事都免费拿到。这是本仓把惯用法
用在正确位置的代表。

## 7. 值得肯定的四处

1. **Composite 树 + 一键式绘制**（§2.1）：新增控件零成本获得布局/裁剪/命中/主题/调试支持。
2. **`ListView` 的 Template Method**（§3.1）：三个纯虚 + 三个共享步骤，`Table`/`TreeView` 各自
   不到 300 行就具备完整滚动列表能力；UI-46 改滚动条配色只动一处，三视图同时生效。
3. **角色表替代颜色分支**（§2.5、§3.2）：颜色令牌直读 129 → 76、手写状态三元式 6 → 0
   （UI-40 实测），控件内不再出现 `mix_color`。
4. **`Target` 的令牌代理**（§2.7）：用一个 `weak_ptr<const bool>` 解决了 UI 里最常见的悬垂
   指针问题，且调用点零改动（隐式转换）。

## 8. 风险与反模式观察

按"证据强度 × 影响面"排序。

### R1（高）`Widget` 宽接口：54 个虚成员 × 42 个子类

`widget.hpp` 有 54 处 `virtual`，其中 30+ 是交互钩子（`on_mouse_down` / `on_hover` /
`on_key_down` / `on_char` / `on_long_press` / `on_focus_gained` …）。后果：

- 加一类交互 = 改基类 = 42 个子类重新编译（虽然空实现不产生代码，但头文件依赖是全局的）；
- 派生类难以判断"哪些钩子必须覆写"，只能读注释；
- 与 UI-37（`set_pos/set_size` 等 setter 17→10 的收敛）同一个问题：**基类膨胀**。

相比之下 `ListView`（3 个纯虚）与 `Drawable`（1 个纯虚）的接口窄得多，说明这不是全仓风格，
而是 `Widget` 一个类的历史积累。

### R2（高）每控件 1,688 B 过渡缓存，且无注释说明取舍

`widget.cpp:124`：`if (transition_ == nullptr) transition_ = std::make_unique<StyleTransition>();`

- 触发条件很低：任何一次 `visual_style()` 调用（hover 一次就够）；
- 生命周期：直到控件析构，不释放、不降级；
- 实测规模：1000 个交互过的控件 ≈ 1.7 MB（12 槽 × 140 B）。

诊断面板类场景（`DebugWindow` 递归所有控件）会加速这个增长。可考虑的替代：按主题共享
`(role, state)` 插值表 + 控件存 4 字节槽号；或 `from/to` 换成"事件时间戳 + 起止色索引"。

### R3（中）Observer 三套并存，消费语义不一致

`bool`（`on_mouse_down/on_click/on_key_down`）、`void`（`on_hover/on_focus_*`）、
`std::function`（`on_select`/`add_event`）三套。调用方（`ui_system.cpp` dispatch）必须逐个记住
哪类能"吃掉"事件。没有统一事件总线是有意的（省掉订阅生命周期），但**语义可以统一**：
把 `void` 钩子也返回 `bool`（默认 `false`）不需要额外成本。

### R4（中）双容器（children + overlays）导致"漏一处就是 bug"

见 §2.1 末尾。已出现过一次真实缺陷（`clear_layout_dirty` 未递归，UI-45 修）。缓解手段：
把"所有需要双遍历的操作"集中到一个 `for_each_child(visitor)` 帮助函数里，而不是各写两遍。

### R5（中）`Theme::with_*` 手写五份，字段清单重复

见 §4.2。已出现过"密度只缩放部分字段"的缺陷（T38/UI-43）。缓解手段：把 `with_*` 实现成
"先 `*this` 拷贝，再调用一个私有 `apply_density()`"，把字段清单收敛到一处。

### R6（中）`DrawList` 的括号配对非 RAII

`push_clip/pop_clip`、`push_opacity/pop_opacity` 要求调用方严格配对（`drawable.hpp:92-113`）。
`Widget::append_to` 里若有 `return` 提前退出就会泄漏一层裁剪。当前靠人工纪律（每个
`push_clip` 后面紧跟一个 `pop_clip`），42 个控件的 `append_to` 都要守这个约定。
`LayoutPassScope` 已经证明了 RAII 在本仓可行，`ClipScope`/`OpacityScope` 是同一套路的缺失。

### R7（中）`Renderer` 与 `Editor` 的体积/职责

`renderer.cpp` 1,434 行（占 backend 层 58%）、`editor.cpp` 976 行。前者是 `backend #1`
已指出的上帝对象，本次复核仍成立；后者是 Mediator 滑向上帝对象（§3.8）。

### R8（低）Command 的幂等契约无编译期保证

`command.hpp:13-15` 用注释约定 `apply/revert` 幂等成对；`CompoundCommand::apply` 无部分失败补偿。
现有 11 个命令都是纯字段改写（不会失败），所以是"未来风险"而非现实缺陷。

### R9（低）`collect_hit_path` 每次指针移动都分配 vector

`ui_system.cpp:171-176` 返回 `std::vector<Widget*>`。鼠标移动事件频率高（>60/s），
可改为成员缓冲区 + `std::span` 复用。

## 9. 缺失的模式（以及为什么可能不需要）

| 缺失 | 若引入的收益 | 本仓为何可以不引入 |
|---|---|---|
| **统一事件总线 / 发布订阅** | 跨层通知（设置变更 → 多面板刷新）不必层层回调 | 现有规模下 `Editor` 作中介已够；总线会引入订阅生命周期与顺序不确定性 |
| **Widget 构造 Builder** | 声明式搭树，减少 `set_pos/set_*` 噪音 | UI-37（setter 17→10）正朝 `LayoutSpec` 快照方向走，比 Builder 更贴合布局语义 |
| **经典 Visitor（`accept`）** | 调试面板可访问控件专有字段 | 会让 42 个子类各加一个方法，收益不抵基类膨胀 |
| **PImpl** | 头文件瘦身、编译期隔离 | 编译单元已按 OBJECT 库拆分（`docs/ci.md`），收益被抵消 |
| **Flyweight（过渡缓存）** | 节省 ~1.7 KB/控件（R2） | 当前规模（编辑器数百控件）内存不是瓶颈，但**建议先加注释记录取舍** |
| **显式状态机（State 类）** | 复杂交互（拖拽/多选/模态）易读 | 现有多为布尔+枚举；`StyleTransition` 已是"最小状态机"，够用 |

## 10. 建议（按价值/成本排序）

| # | 建议 | 对应风险 | 成本 | 收益 |
|---|---|---|---|---|
| 1 | 给 `StyleTransition` 的 1.7 KB 取舍加注释（或改共享表） | R2 | 极低 / 中 | 避免被误认为零成本；后者省 ~1.7 KB/控件 |
| 2 | 把 `void` 交互钩子统一为 `bool`（默认 `false`） | R3 | 低 | 消费语义一致，dispatch 分支可简化 |
| 3 | 抽 `for_each_child(visitor)`，消除双容器双遍历 | R4 | 低 | 消除"漏一处"类缺陷的成因 |
| 4 | `ClipScope`/`OpacityScope`（RAII）替代 `push_/pop_` | R6 | 低 | 提前 `return` 不再泄漏裁剪层 |
| 5 | `with_*` 收敛到单一 `apply_*` 私有实现 | R5 | 低 | 新增主题字段不再漏缩放 |
| 6 | `Editor` 拆分：命令分发 / 面板装配 / 密度主题应用 | R7 | 中 | 976 行 → 三份 ~300 行 |
| 7 | `Widget` 交互钩子分组（接口隔离：`PointerTarget` / `KeyTarget` / `FocusTarget`） | R1 | 高（破坏性） | 与 UI-37 同向，宜合并推进 |

> 基类从"什么都放"收敛成"按能力分组"。分两次做会互相冲突，建议合并成一个接口收敛专项。

## 11. 结论

- 本仓的设计模式使用是**克制且一致**的：核心只有四条主线——**Composite（树）、Template Method
  （骨架）、Strategy（数据化策略）、Command（可撤销编辑）**，其余模式都在"刚好够用"的粒度上。
- 最值得保留的特征是"**用数据和函数替代继承**"：角色表、`resolve_main_axis`、`Theme::with_*`
  都是把变化点收敛成数据，而不是引入运算符重载式的类层次。
- 主要技术债不是"模式用错"，而是**基类膨胀（`Widget` 54 虚成员）**、**每控件 1.7 KB 过渡缓存
  的隐性成本**、**双容器遍历的复制粘贴**，以及 `Renderer`/`Editor` 两个体积过大的类。
- 已发生的三次真实缺陷（`clear_layout_dirty` 未递归、密度缩放漏字段、滚动条滑块同槽覆盖）
  都落在"约定靠注释/纪律、没有类型或结构保证"的位置——这与本报告的 R2/R4/R5 完全对应。
