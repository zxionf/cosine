## 1. 现有链路

```
Theme（62 个令牌字段：32 颜色 + 25 度量 + 5 策略）
 ├─ Theme::style(role, state) → BoxStyle{fill, border, border_width, radius, text, text_size, focus_ring}
 │    ├─ Widget::visual_style()  → StyleTransition（单槽缓存，带过渡）   ← 11 个调用点 / 9 个控件
 │    └─ t.style(...) 直调（无过渡、无缓存）                            ← 23 处 / 13 个文件
 └─ 控件直读令牌 t.accent / t.checkbox_fill / t.slider_handle …        ← 138 处 / 24 个文件

焦点环：Widget::append_focus_ring() 直接读 t.accent + t.focus_thickness/offset（不经 BoxStyle）
命中/布局：padding / spacing / control_height 等度量令牌另有 315 处直读（含颜色）
```

三个入口并存（角色表 / 过渡包装 / 令牌直读）是这个系统最主要的形态特征，也是绝大多数问题的来源。

## 3. 问题清单

### P0-1 单槽 `StyleTransition` × 多角色控件：颜色串台（**已复现**）

`Widget::visual_style()`（widget.cpp:85-105）为每个控件只维护**一个**过渡槽：

```cpp
if (transition_->role != role || transition_->state != state) {   // widget.cpp:97
    transition_->from = current_transition_style();               //  :98  取"上一角色"的当前色
    transition_->to = target;
    transition_->role = role;
    transition_->state = state;
    transition_->progress = transition_duration() <= 0 ? 1 : 0;   //  :102 归零
}
return current_transition_style();                                //  :104 progress=0 → 返回 from
```

同一控件在一次 `append_to` 里请求两个不同角色时，第二次调用会：
1. 把 `from` 设成**前一个角色**的当前色；
2. `progress` 归零，于是本次返回 `from`（即前一个角色的颜色）；
3. 下一帧 `advance_transition()` 只推进最后写入（第二个）角色，第一角色永远推进不到目标。

`Slider::append_to` 正是这种写法（slider.hpp:74 / 81 / 124：Track → Accent → Tooltip）。

**探针实测**（链接 `build/src/libcosine_ui.a` 的临时程序，60fps、`transition_ms=120`，
Slider 值 > 最小值以触发 Accent 分支；颜色为线性值直接×255 打印）：

```
target track  = #0B0D0F     target accent = #0C45CE
frame 0: track=#0B0D0F  fill=#0B0D0F      ← 填充直接用了轨道色
frame 1: track=#0B1B40  fill=#0B1B40      ← 两者同色
frame 2: track=#0B2665  fill=#0B2665
frame 4: track=#0C3494  fill=#0C3494
frame 7: track=#0C3EB6  fill=#0C3EB6      ← 轨道整体向 accent 收敛
```

即：**滑块轨道与已填充段最终同色，轨道被染成强调色**；`Track` 的 `track_hover` 也不再可能生效。

旁证（说明这不是"作者没注意"，而是设计约束已被绕过）：

| 控件 | 用到的角色 | 采取的策略 | 位置 |
|---|---|---|---|
| Slider | Track + Accent + Tooltip | 直接用 `visual_style`（**踩坑**） | slider.hpp:74/81/124 |
| Progress | Track + Accent | 绕开 `visual_style`，改 `t.style()`，**放弃过渡** | progress.hpp:58-61 |
| Checkbox | Control（+ 勾选块） | 注释明写"不要用 `visual_style(Accent)`，会覆盖过渡缓存" | checkbox.hpp:72-74 |
| Radio | Control（+ 选中标记） | 同上 | radio.hpp:81-83 |
| ScrollView / Table / TreeView / MenuBar / Dropdown / PreviewRuler / Tooltip / TabBar | 各 1 角色 | 全部走 `t.style()` 直调，无过渡 | 23 处 |

同一角色组合在三个控件里出现三种不同解法，说明 API 的"一控件一角色"假设没有表达出来。

**修复方向**（择一，见 §6）：过渡槽按角色分（8 个 slot 的定长数组）；或控件声明自己使用的角色集合；
或把 `StyleTransition` 从 `Widget` 移到"角色使用方"手里。

### P1-2 双轨：角色表只覆盖了约 20% 取色

- 角色路径：11 次 `visual_style` + 23 次 `t.style` = 34 个取色点；
- 令牌直读：138 个颜色读取点，分布在 24 个文件。

典型越轨：

| 位置 | 现象 |
|---|---|
| `window.hpp` append_to | 标题栏底色用 `t.button_hover`（Control 的 hover 态令牌）当"chrome"底色；边框用 `t.elevated_border`/`t.accent` 手判 `is_focused()\|\|active` |
| `scroll_view.cpp:319-323` | 轨道走 `Track` 角色，滑块却直读 `t.scrollbar_thumb`；`Theme::scrollbar_track` 无人使用 |
| `checkbox.hpp:63-74`、`radio.hpp:72-83` | 框体直读 `t.checkbox_bg/border`，勾选块直读 `t.checkbox_fill`，绕过 Control/Accent |
| `slider.hpp:86-92` | 手柄直读 `t.slider_handle` 并手写 `mix_color(handle, accent, 0.15/0.35)` 表达 hover/drag |
| `panel.hpp:50` | hover 边框色手写 `is_hovered() ? t.accent : style.border`（Surface 无 Hovered 语义） |
| `editor.cpp` / `editor.hpp` | 应用层直读 `accent`/`splitter`/`window_bg`（可接受，但说明缺"应用级角色"） |

后果不是"代码丑"，而是**主题化能力受限**：换一套配色需要同时改 `Theme` 字段与控件代码；
`Accent` 与 `checkbox_fill`/`slider_fill`/`text_input_selection` 这些同义令牌无法保证一致。

### P1-4 `Accent` 文字色硬编码，浅色主题对比度不足

`style.hpp:110` 在角色表里直接写死 `s.text = srgb_hex(0x0F1419)`。按 WCAG 相对亮度估算：

| 主题 | accent | 硬编码文字色 | 对比度 |
|---|---|---|---|
| dark | `#3D8EE8` | `#0F1419` | ≈ 5.6:1 ✓ |
| light | `#1F6FD0` | `#0F1419` | ≈ **3.8:1** ✗（正文级需 4.5:1） |

`Theme::accent_text` 是为"蓝底上的蓝字"准备的，但没有"accent 上的文字色"令牌；
浅色主题下按钮/选中块上的文字会偏灰暗、对比不足。

### P1-5 角色不带字号档位

`style.hpp:61` 固定 `s.text_size = text_size`，所以 `BoxStyle` 永远只给出 `Theme::text_size`；
`small_text_size` / `heading_text_size` 只能由控件直读主题（7 处：timeline_view、preview_ruler×3、
tooltip×3、image、editor…）。

结果：Tooltip（角色 `Tooltip`）想用 12px，但拿到的是 16px 的颜色语义 + 直读主题的字号，
角色表无法表达"这类控件字号更小"，`MenuItem` 的快捷键文字也只能手写小字号。

### P2-6 状态语义缺口

| 缺口 | 现象 |
|---|---|
| 无 Selected/Checked 态 | 行选中由控件手叠 `accent` 半透明（table/tree），勾选由 `checkbox_fill` 直读；两者都不是状态 |
| Row/MenuItem 的 Disabled 未定义 | 落到 `default: break;`，即"无填充 + 正常文字色"，禁用行看起来仍可用 |
| 状态推导双入口 | `control_state()`（6 处）与手写三元式并存（slider.hpp:74、splitter.hpp:128：`is_hovered() ? Hovered : Normal`，Disabled 被忽略） |
| 焦点不是状态 | 焦点环独立于 `ControlState`（设计如此），所以"禁用且聚焦"没有明确表现 |

### P2-7 主题可变性的边界不闭合

- `UIContext::theme` 是 **public 可变字段**，直接改不会 `bump_theme_revision()`；
  而过渡缓存只在 revision 变化时重建（widget.cpp:90-96），于是"直接改主题 + 控件已有 transition_"
  = 继续用旧色，直到该控件下一次 hover。
- `theme_revision()` / `mutable_theme()` 是**进程级全局单例**（theme.hpp:202-234），
  与"主题挂在 UIContext 上"的模型不一致：多 root / 多 context（ui_lab、测试）互相打断缓存。
- `visual_style()` 是 `const` 成员却通过 `mutable transition_` 改状态（widget.hpp:398），
  绘制期写状态：同一控件一帧内被绘制两次（如同时挂 overlay）会互相踩。

### P2-8 两套密度机制并存且数值不同

| 机制 | 影响项 | 位置 |
|---|---|---|
| `Theme::with_density()` | 10 项度量 + 3 个字号 + 6 个 radius（共 19 项） | theme.cpp:5-31，被 ui_gallery/ui_lab 使用 |
| `Editor::apply_theme()` 的 `kDensity[3]` 表 | 仅 control_height / padding / spacing | editor.cpp:894-914 |

后果：settings 里的 density 档位不缩放 `checkbox_size`/`scrollbar_width`/`radius`，
而同样档位在示例程序里会缩放；两套数值也不一致（compact：表里 padding=6，
`with_density` 得到 8×0.85=6.8）。CO-7 里删掉的 `base.padding = 0.0f` 就是被这张表覆盖的死代码。

### P3-9 其他

- `with_rounding(false)` 与 `with_radius_scale(0)` 语义重叠（都归零 radius），`apply_theme` 两者都调（editor.cpp:889-890）。
- `Theme` 62 个扁平字段无分组（颜色/度量/策略混排），加字段全靠命名纪律。
- `BoxStyle` 按值返回（6×vec4 + 4 float ≈ 120B），每帧每控件；`Theme::style` 内联在 `style.hpp`，23 个 TU 重编。
- `lerp_style` 只混合 4 个颜色字段、几何取目标值（已文档化）；焦点环、文字在过渡中不变（可接受，但与"过渡"命名不完全一致）。

## 4. 与 ui #1 的关系 / 本轮变更

ui #1 未覆盖样式系统，只把"文本度量 8–10 处散落"列为遗留，并把 `UI-11 主题令牌对照表` 挂在 UI 线（todo）。

本轮 CO-7（commit `36bbdc6`）首次触碰了样式系统的**边界语义**：

- `Widget::set_padding()` 现在代表"调用方显式意图"（锁定），主题只能通过 `apply_theme_padding()`
  注入未设定的控件（widget.hpp:167-180，docs/ui_architecture.md 契约 6）；
- 这是"用户覆盖 vs 主题注入"的第一个先例，但**只解决了 padding**：
  `Panel::set_context()` 仍在无条件 `set_spacing(context->theme.spacing)`（panel.hpp:32），
  `TabView` 的行间距同理——同一类问题还留着两处。

## 5. 缺失能力（明确不在本次范围）

1. 无"密度/字号/圆角"的角色级表达：角色只能给颜色与圆角档位。
2. 无主题校验：令牌之间的一致性（accent 与 checkbox_fill、focus 与 accent）靠人眼。
3. 无样式快照回归：`test_ui_render_snapshot` 只覆盖 Table/TreeView，样式改动仍凭截图判断。
4. 无"禁用/选中"的语义化状态（见 P2-6）。

## 8. 评估方法

- 结构结论来自对 `theme*/style*/widget*` 的完整阅读 + 对 24 个消费方文件的定向 grep（命令见 §7）。
- P0-1 是**运行时复现**：临时探针（链接 `libcosine_ui.a`，源码见附录）连续 8 帧打印
  `visual_style(Track)` 与 `visual_style(Accent)` 的 `fill`：第 0 帧两者就相等（填充拿到的正是
  轨道目标色），随后整体向 accent 收敛；`transition_ms=120`、60fps 下轨道因此变成强调色。
  探针位于仓库外（`/tmp`），未提交。
- 对比度数值按 WCAG 2.x 相对亮度公式手算（sRGB → 线性 → `(L1+0.05)/(L2+0.05)`），量级可靠，
  不用于像素级验收。
- §3 中除 P0-1 外均为**静态推断**（阅读代码得出、未做运行时验证），标注为"待确认"的性质与 ui #1 §6 相同。
