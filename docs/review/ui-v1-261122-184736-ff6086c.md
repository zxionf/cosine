## 2. 架构现状

```
Widget（身份 / parent / 几何 / 可见性 / Layer / z_index）
 ├─ children_ + adopt()              ← 唯一挂载入口
 ├─ measure 契约 + fixed_size()      ← 布局契约
 ├─ layer_paint_order()              ← 唯一排序入口（本轮新增）
 │     layer 升序 → z 升序，稳定；绘制正序 / 命中反序 / Tab 正序
 │     children_ 与 overlays_ 合并排序，overlay 不再是一等顺序来源
 ├─ preferred_focus()                ← 模态初始焦点钩子（本轮新增）
 └─ Layer{Content,Floating,Modal}    ← 已接线（本轮从「声明」变为「驱动」）

UIRoot
 ├─ 模态栈 modals_ / modal_scrims_ / modal_focus_stack_（同步维护）
 ├─ 焦点钩子（UISystem 注入 getter/setter，避免 UIRoot 依赖 UISystem）
 └─ layout() 归一化模态帧 z（scrim 2i+1 / window 2i+2）+ 剔除悬空帧

UISystem
 ├─ pointer_pos() / framebuffer_to_logical()  ← 逻辑坐标出口（本轮新增）
 └─ dispatch_key/char 按 modal_top() 子树收窄

  GLFW 窗口坐标 ──Window::cursor_to_framebuffer（×DPR）──▶ framebuffer
  ──UISystem::framebuffer_to_logical（÷ui_scale）──▶ UI 逻辑坐标

行为基元：ScrollState · ListView · CollapsibleHeader · Scrim · FontAtlas::centered_text_y
容器：Vbox / Hbox / Grid / Wrap / Panel / Splitter / ScrollView / UIRoot / Window / Section / Dialog / TabView
```

## 3. 本轮修掉的真实问题

1. **嵌套模态 z 冲突**：此前两个模态窗口都是 `kOnTopZ=10000`、两个 Scrim 都是 9999，靠 `children_` 插入顺序兜底。现在 `layout()` 确定性分配 `frame i → scrim 2i+1 / window 2i+2`，不再靠巧合。
2. **`modals_` 悬空指针**：窗口被父容器直接销毁（未走 `release_modal`）时，`modal_top()` 会解引用野指针。现在 `layout()` 剔除不在树中的帧并清掉残留 Scrim。
3. **对话框键盘穿透**：`DialogHost` 是 overlay，此前只有调用方手写 `set_focus` 才有焦点，键盘可穿透到下层。现在经 `push_modal(host, with_scrim=false)` 纳入模态作用域，`dispatch_key`/`dispatch_char` 自动收窄。
4. **moss 鼠标坐标差 2 倍**：`Application::ui_scale_` 是 private，moss 只能手动设 renderer/uisys 而漏掉鼠标换算用的那处，命中测试用物理坐标比对逻辑尺寸。`set_ui_scale` 单一入口后不再有漏同步路径。

## 5. 仍然存在的结构性问题（明确不在本轮范围）

1. **滚动状态 3 套**：`ScrollView` 自管二维、`ListView` 用 `ScrollState`、`TreeView` 自管。与 #5 §3.2 结论一致，未变。
2. **行列表 2 套**：`ListView` 提供契约，`Table::append_to` 仍自己画行。UI-10，前置「先补渲染快照对比」。
3. **文本度量 8–10 处**：各控件各写 `atlas ? measure(...) : size * 0.5f`。未收敛。
4. **浮层生命周期所有者仍多**：`MenuScrim` / `DropdownScrim` / `DialogHost` / 子菜单各自管生命周期。本轮统一了**排序**（Layer），但**生命周期**仍分散——「浮层与模态 2 套机制 × 4 个所有者」里的后一半还在。
5. **`Widget` 366 行 12 种职责**：通过显式契约缓解，未拆分（T05 有意不做）。
6. **`menu_bar.hpp` 859 行**：菜单语义的合理复杂度，拆开反而分散（T06 有意不做）。

## 6. 本轮暴露的新语义边界（需后续决策）

1. **`Layer` 与模态栈是正交的两套机制，`DialogHost` 处于中间态**：
   - `DialogHost::layer()` = `Floating`，但它又通过 `push_modal(host, with_scrim=false)` 进入模态栈（拥有键盘/焦点隔离）。
   - 而模态 `Window::layer()` = `Modal`。按排序 `Floating < Modal`，**同时存在模态窗口 + 对话框时，模态窗口会盖住对话框**（绘制与命中都先于 DialogHost）。
   - 触发场景：从模态窗口内再弹对话框（打开/保存等）。当前 cosine 是否存在该场景待确认；若存在需把 `DialogHost` 提到 `Modal` 层，或在排序上让「模态作用域的顶层」不受 layer 限制。
2. **`Scrim::set_on_dismiss` 是预留能力，无消费者**：`Window` 模态默认不因点遮罩关闭，`DialogHost` 用自己的遮罩。该 API 目前是死代码，需在某个产品路径真正接上或明确删除。
3. **焦点栈 `modal_focus_stack_` 与 `modals_` 三处强同步**：`push_modal` / `pop_modal` / `layout()`（悬空帧剔除）都要同时维护三个 vector。当前靠代码纪律保证，无测试直接覆盖「三数组长度恒等」的不变量。
