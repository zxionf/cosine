## 0. 结论摘要

backend 层结构清晰，除 **`Renderer` 是典型的上帝对象**（1434 行 `.cpp`，占全层 59%，约 60 个方法、10 种职责）外，其余组件职责单一、规模合理。

最尖锐的问题不是"代码多"，而是：

1. **`Renderer` 集成了 10 种互不相关的职责**，任何一处改动都要重编译/重读整个文件；
2. **零 Vulkan 渲染单元测试**——`render_offscreen` 不参与 ctest，渲染正确性全靠 lavapipe 冒烟（只验启动 + validation 干净，不做像素比对）；
3. 单窗口 / 单 Renderer 假设（R14）仍然开放，阻碍多窗口。

## 2. 架构现状

```
graphics/（DrawList · DrawBatch · Vertex · FontAtlas）——「画什么」，与 Vulkan 解耦
        │ append_to / 顶点数据
backend/ ──────────────────────────────────────────────────────
  window             GLFW 封装 + DPR（framebuffer/window）+ 光标换算
  asset_path         资产路径解析（纯逻辑，有测试）
  vulkan/
    vulkan_context   instance · debug messenger · surface · device · queue
    swap_chain       swapchain · images · views · recreate
    render_target    渲染目标结构（swapchain 或离屏 image）
    renderer         ← 上帝对象（见 §3）
```

分层依赖单向：`graphics` 不依赖 backend；`renderer` 依赖 `vulkan_context` + `swap_chain` + `graphics`。

## 3. 核心问题：`Renderer` 上帝对象

`renderer.cpp` 的函数清单按职责归类：

| 职责 | 行区间（约） | 规模 | 说明 |
|---|---|---|---|
| 管线 | 45–210 | ~165 | descriptor set layout + pipeline + shader 加载 |
| 纹理/图片槽 | 221–488 | ~270 | white/placeholder、上传、清空、槽描述符、字体图集上传 |
| 图像/缓冲工具 | 516–688 | ~170 | create_image/view/buffer、copy、layout transition、find_memory_type |
| uniform/descriptor | 689–775 | ~86 | uniform buffers、descriptor pool/sets |
| 命令/同步 | 211–240, 600–652, 776–805 | ~110 | command pool/buffers、单次命令、semaphore/fence |
| 帧循环 | 963–1162 | ~200 | begin/end、begin/end_frame、begin/end_rendering |
| 绘图 API | 837–962 | ~125 | draw、scissor、line/rect/triangle/char/text |
| 离屏/PNG | 1194–1377 | ~183 | render_offscreen、readback、write_png、record_batches、upload_vertex_data |
| push/uniform 更新 | 806–836 | ~30 | update_uniform_buffer / update_push_constants |

外加 `renderer.hpp` 里约 40 个成员（管线、纹理、缓冲、同步、字体、图片槽、帧状态），成员之间的生命周期耦合极高（例如图片槽重建要回写所有帧的 descriptor set）。

**后果**：
- 改一个"离屏导出"或"图片槽"功能，要在 1434 行的文件里导航；
- 无法为"管线/纹理/同步"单独写单元测试（它们被 `Renderer` 的构造时序焊死）；
- 新功能（如多窗口、离屏导出、纹理 LRU）都倾向于继续往这个类里堆。

## 4. 测试覆盖缺口（比上帝对象更尖锐）

| 测试 | 覆盖 | 是否渲染 |
|---|---|---|
| `test_asset_path` | 资产路径解析 | 否（纯逻辑） |
| `test_render_target` | `RenderTarget` 结构体字段 | 否（纯逻辑） |
| `testglfwinit` | GLFW 初始化 | 否（无 Vulkan） |
| **渲染正确性** | — | **无单元测试** |

- `render_offscreen` 已有离屏 + 读回能力，但**没有任何 ctest 用它做像素断言**；
- 唯一接近的是本次 UI 迁移新加的 `test_ui_render_snapshot`（离屏渲染 Table + FNV 哈希对比），但它**不进 ctest**，仅作手动工具；
- 冒烟靠 `scripts/smoke-lavapipe.sh`，只检查「能启动 + 无 validation error」，**不做像素比对**（`docs/ci.md` 已明确）。

**结论**：任何渲染/管线的回归，在 CI 里都不可见；唯一能拦住它们的，是运行时的 validation layer，而非像素级或行为级测试。

## 6. `Renderer` 拆分建议（若做）

按职责拆，不改行为，只挪成员与函数：

```
Pipeline          descriptor_set_layout + pipeline + shader_module（45–210）
TextureManager    white/placeholder/字体图集/image slots/upload/clear（221–488）
BufferAllocator   create_image/view/buffer、copy、transition、find_memory_type（516–688）
FrameLoop         begin/end/begin_frame/end_frame/同步对象/命令（963–1162 + 同步）
OffscreenExporter render_offscreen/readback/write_png/record_batches/upload_vertex_data（1194–1377）
Renderer          仅做组合 + 绘图 API + push/uniform 更新
```

**风险与前置**：拆分是纯重构，收益是"可单独测试 + 可读性"，但会改大量成员访问路径，且**当前无渲染单元测试做安全网**——所以**正确顺序是：先补 B2（渲染测试）→ 再拆 B1**。若只做一件，先做 B2。
