## 0. 结论摘要

当前版本已经不是早期的 UI 原型：分层、上下文、事件令牌、延迟 overlay、文本图集、表格/菜单/对话框等基础都在，`examples/ui_gallery` 也能作为较完整的验收场景。

但仍有几个问题会直接导致崩溃、事件失效或交互错乱，建议按下面的顺序处理：

1. **P0：事件回调中销毁控件后的悬空访问**。控件回调里调用 `clear_children()`、`set_content()`、`set_page()`、`Splitter::set_panes()` 等立即销毁型 API，或回调销毁当前/祖先控件时，`bubble_to_root()` 和 `Target` 的裸指针路径可能继续访问已释放对象。
2. **P0：`Target` 的有效性检查可被隐式绕过**。`Target::operator Widget*` 直接返回裸指针；滚动、鼠标抬起等路径没有先检查令牌有效性，且 GLFW 事件在 `UISystem::tick()` 之前派发，`prune_stale_targets()` 来不及清理。
3. **P0：顶点/索引缓冲没有容量检查**。`Renderer::upload_vertex_data()` 超过 `MAX_VERTICES_` / `MAX_INDICES_` 时会越界写入 staging buffer，属于内存破坏。
4. **P1：`ScrollView` 的条带计算不是不动点**，双轴滚动条可能出现条压内容、视口尺寸错误；命中测试也没有裁掉滚动条区域，滚动条下方的按钮可能先吃掉点击。
5. **P1：`ScrollPanel` 的构造函数高度被 `measure()` 忽略**，未额外设置 min/max 时会随内容长高而不是滚动；gallery 目前通过显式设置精确 min/max 规避了这个问题。
6. **P1：公共头文件暴露 Vulkan，但目标没有 PUBLIC 传播 Vulkan include/link 依赖**，Windows SDK 布局下测试/下游目标可能编译失败。
7. **P1：overlay 所有者生命周期和 `UIRoot::clear_overlays()` 的立即销毁** 可能留下悬空的 `Dropdown`/`MenuBar` 所有者指针。

严重度统计：**P0 3 项，P1 7 项，P2 11 项**。不计入新缺陷的已知设计限制见第 10 节。

## 4. P0：会导致崩溃或内存破坏的问题

### P0-1 事件回调中销毁控件或祖先，`bubble_to_root()` 立即变成悬空访问

位置：

- `src/ui/ui_system.cpp:9-14`
- 事件派发入口：`src/ui/ui_system.cpp:199-200`、`:222-224`、`:237-239`、`:255-262`、`:288-291`、`:298-300`

`bubble_to_root()` 目前的形式是：

```cpp
for (Widget* widget = start; widget; widget = widget->parent()) {
    if (callback(widget)) return;
}
```

问题不在循环本身，而在 **`callback` 是可重入的用户代码**。回调里只要执行以下任一操作，当前 `widget` 或它的父节点就可能立刻被析构：

- `Vbox/Hbox::clear_children()`：`src/ui/vbox.hpp:18`、`src/ui/hbox.hpp:18`
- `ScrollView::set_content()`：`src/ui/scroll_view.cpp:9`
- `TabView::set_page()`：`src/ui/tab_view.hpp:59`
- `Splitter::set_panes()`：`src/ui/splitter.hpp:22`
- `RadioGroup::set_options()`：`src/ui/radio_group.hpp:24`
- `List::clear_items()`：`src/ui/list.hpp:28-31`

这些 API 都是立即销毁，不是延迟到 `tick()`。典型崩溃路径：

1. 鼠标按下命中列表项/按钮，`pressed_` 保存目标。
2. `on_click` 回调里调用 `set_content()`/`clear_children()`，目标自身或父容器被销毁。
3. `bubble_to_root()` 在回调返回后读取 `widget->parent()`，或继续把已释放的祖先传给回调。
4. `dispatch_mouse_button()` 在 `on_mouse_up` 返回后还会比较 `pressed == target`，再对可能的已销毁 `pressed` 调用 `on_click`。
5. GLFW 的多个事件在同一次 `glfwPollEvents()` 中派发，而 `UISystem::tick()` 在轮询之后才调用；`prune_stale_targets()` 无法在这些事件之间兜底。

这不是理论问题：`examples/ui_gallery` 的导航、分页、列表和对话框接线都允许回调修改 UI 结构；任何后续控件按同样方式接线，都可能复制这条路径。现有 `test_ui_dropdown` 只在派发之外调用 `clear_children()`，没有覆盖“回调内部销毁”。

建议：

- 短期：事件派发期间禁止结构性立即销毁。`clear_children()`、`set_content()`、`set_page()`、`set_panes()`、`set_options()`、`clear_items()` 改为把旧对象移入延迟回收队列，到 `tick()` 的 layout 前统一释放。
- 中期：给 `bubble_to_root()` 的路径使用“目标令牌 + 父链快照”，每次回调返回后重新验证；不要从可能已销毁的 `widget` 读取 `parent()`。
- 事件捕获层统一使用 alive token，`pressed_`、`hovered_`、`focused_` 只暴露强校验后的对象。
- 增加回归测试：在 `on_mouse_down`、`on_mouse_up`、`on_click`、`on_scroll`、`on_key_down` 中分别销毁自身、父容器、祖先容器；在 ASAN 下运行。

### P0-2 `Target::operator Widget*` 绕过有效性检查，同一次 poll 内可复用失效目标

位置：

- `src/ui/ui_system.hpp:52`
- `src/ui/ui_system.cpp:244`（鼠标抬起取 `pressed_`）
- `src/ui/ui_system.cpp:268`（滚轮直接取 `hovered_`）
- 对比：`src/ui/ui_system.cpp:198`、`:286`、`:297` 使用的是 `explicit operator bool()`，只检查令牌有效

`Target` 同时提供“显式 bool 检查”和“隐式转 `Widget*`”两种接口。只要写 `Widget* w = target;` 就会绕过有效性检查，拿到裸指针。当前代码里至少有两处直接这样用：

- 鼠标抬起：`Widget* pressed = pressed_;`
- 滚轮：`Widget* target = hovered_;`

即使 `prune_stale_targets()` 在 `tick()` 里能清掉失效目标，它运行得太晚：GLFW 一次 `poll` 可能连续给出 mouse down、mouse up、mouse move、scroll。如果 down 的回调把目标销毁了，紧接着的 up/scroll 仍会拿到旧裸指针。`dispatch_mouse_button()` 中 `target` 还直接来自 `hit_path()` 的裸指针路径，没有保存/验证路径节点令牌。

建议：

- 删除 `Target::operator Widget*`，只允许通过 `get()`/`widget()` 获取，并且要求先 `valid()`。
- `Target` 除了 alive token，还保存树身份（root 序号或节点 id）；`hit_path()` 返回带令牌的路径项。
- `dispatch_mouse_button()` 在按下时保存带令牌的 `pressed_`，抬起时先验证，再派发。
- `dispatch_mouse_scroll()` 不要直接读 `hovered_`，统一通过 `hovered_.valid()` + `tree_contains()`。
- 事件派发前，在同一次 poll 内的每个事件之间也可以执行一次轻量 `prune_stale_targets()`；但它不能替代回调内部销毁的防护。

### P0-3 顶点/索引缓冲没有容量检查，超过 65,536 个 quad 会越界

位置：

- `src/backend/vulkan/renderer.hpp:187-188`：`MAX_VERTICES_ = 262144`、`MAX_INDICES_ = 393216`
- `src/backend/vulkan/renderer.cpp:1070-1093`：`upload_vertex_data()`
- 缓冲区分配：`src/backend/vulkan/renderer.cpp:1039-1067`

`MAX_VERTICES_` 对应 `65,536` 个 quad（每个 quad 4 顶点），`MAX_INDICES_` 对应同样数量的 quad（每个 6 索引）。但 `upload_vertex_data()` 只是把每个 batch 的 `vertices`/`indices` 直接 `memcpy` 到映射的 staging buffer，并执行 `copyBuffer`，**没有检查累计大小是否超过分配尺寸**。

一旦单帧超过 65,536 个 quad，例如大表格、复杂调试叠加、全量 CJK 文本或无分页的大量列表：

- staging buffer 写入越界，可能破坏相邻映射内存；
- `copyBuffer` 的 size 超过 device buffer，触发 Vulkan validation 错误，严重时 GPU/驱动崩溃；
- 错误发生时不一定有可读的“容量已满”日志，定位困难。

建议：

- 在 `upload_vertex_data()` 开头做预检：累计顶点数、索引数分别不超过 `MAX_VERTICES_`、`MAX_INDICES_`。
- 更稳妥的做法是按 batch 拆分到多个容量块，或根据本帧 DrawList 自动扩容；扩容前等待 in-flight fence 并重建缓冲。
- 无法拆分时至少抛出明确异常/记录错误并跳过该帧，而不是越界。
- 增加一个不依赖 GPU 的容量预检测试：构造超过 65,536 quad 的 `DrawList`，验证返回错误而不是进入 `memcpy`。

## 5. P1：影响主要交互、API 正确性或跨平台交付的问题

### P1-1 `ScrollView` 双轴滚动条计算不是不动点，条可能压内容

位置：`src/ui/scroll_view.cpp:33-65`

当前逻辑：

1. 先按原始 `viewport_` 判断 `need_v` / `need_h`；
2. 如果任一需要，先减掉对应方向的条带宽度；
3. 重新测量一次内容；
4. 再判断一次 `need_v` / `need_h`。

问题在于第 3 步重新判断出“另一个方向也需要滚动条”时，**没有为它再减掉另一条条带占用的交叉轴空间**。例如：

- 外框 `200 x 200`，内容 `300 x 195`；
- 初次判断：横向需要，纵向不需要；
- 减去水平条高度后，纵向内容放不下，第二次判断变成纵向也需要；
- 但 `viewport_.x` 没有减去垂直条宽度，垂直条会压在内容右侧；
- 横向滚动上限仍按较宽的视口计算，最右侧约一个条带宽度不可见。

反过来，如果在同一次 `update_metrics()` 中重新测量后条又不需要（例如换行内容在缩窄后变矮/变窄），`viewport_` 也没有恢复为原始大小；条虽然隐藏，视口仍然偏小。

建议：

- 用固定点迭代：最多重复 2～3 次，或者在四个“横/纵是否需要”的组合中求出稳定解。
- 最终 `viewport_ = outer - {need_v ? bar : 0, need_h ? bar : 0}`，再基于最终视口重新测量内容。
- 为“只有水平条 → 后增垂直条”“只有垂直条 → 后增水平条”“内容缩小后条消失”三种情况补测试。现有 `test_ui_scrollbar.cpp` 主要覆盖初始单轴和双轴，不覆盖这个转换。

### P1-2 `ScrollView` 渲染裁剪了内容，命中测试没有裁掉滚动条/视口区域

位置：

- `src/ui/ui_system.cpp:22`：`collect_hit_path()` 只检查当前控件是否 `clips_children()`，没有与祖先裁剪区求交
- `src/ui/scroll_view.cpp:249`：绘制时使用 `viewport_` 裁剪内容
- `src/ui/scroll_view.cpp:182-211`：滚动条自身在 `ScrollView::on_mouse_down()` 中处理
- `src/ui/button.hpp:85-90`：按钮在 `on_mouse_down` 返回 `true`

`ScrollView` 的内容子控件在 `Axis::Both`、子控件有固定/最小尺寸、或内容测量忽略约束时，可以伸到滚动条下方，而 `collect_hit_path()` 仍会把该位置的内容子控件当作最上层目标。结果：

- 鼠标停在垂直滚动条上时，条下面如果正好是按钮，按钮先收到 `on_mouse_down` 并返回 `true`；
- `bubble_to_root()` 因按钮已消费事件而停止，`ScrollView::on_mouse_down()` 的滑块拖动/轨道翻页逻辑永远不执行；
- 点击滚动条可能误触按钮，悬停高亮也会落在被条遮住的控件上。

同样的问题也存在于其它带裁剪的容器（例如 `TabView` 的页内容）：只要子控件在容器外接矩形内，但落在实际裁剪区外，仍可能被命中。

建议：

- 让 `collect_hit_path()` 携带祖先裁剪矩形，递归时与每个 `clips_children()` 控件的实际可视区求交；不要只检查当前控件的外接矩形。
- `ScrollView` 应提供 `hit_clip_rect()`，返回 `{global_.pos, viewport_}`，并让滚动条区域优先于内容子控件命中。
- 或者把滚动条做成真正的子控件，置于内容之上参与命中排序。
- 增加“滚动条下面放一个按钮”的测试：点击滚动条必须不触发按钮，拖动必须改变 offset。

### P1-3 `ScrollPanel` 构造函数高度被 `measure()` 忽略，默认不会滚动

位置：`src/ui/scroll_panel.hpp:42-51`；`ScrollPanel(x, y, width, height)` 位于 `:17-21`

`ScrollPanel` 继承 `Panel`，但 `measure()` 基本按内容高度返回，未使用构造函数传入的 `height`，也没有把测量结果限制在面板自身尺寸内。父布局在未设置 `min_size`/`max_size` 时，会把面板拉高到内容高度，内部 `ScrollView` 也随之获得同样高度，最终“内容全部展开、滚动条不出现”。

目前 `examples/ui_gallery/ui_gallery.hpp:163-164` 通过：

```cpp
panel->set_min_size({kContentWidth, kContentHeight});
panel->set_max_size({kContentWidth, kContentHeight});
```

人为固定了尺寸，所以 gallery 看起来正常；这属于绕过，而不是组件默认行为正确。

建议：

- `ScrollPanel::measure()` 对于显式构造尺寸采用固定高度/宽度，或至少返回 `clamp_size(local_.size)`；内容高度只在未指定尺寸时作为 fallback。
- 明确“固定面板尺寸”和“内容自适应面板”两种模式，不要让调用者必须同时设置 min/max 才能得到构造函数的语义。
- 增加一个只传构造参数、不设置 min/max 的测试，验证面板高度等于构造高度且 `ScrollView::scrollbar_visible(true)` 为真。

### P1-4 `Dropdown` / `MenuBar` 没有析构时关闭 overlay，所有者指针可能悬空

位置：

- `src/ui/dropdown.hpp:140-149`：scrim 捕获 `this`，popup 保存 `Dropdown& owner`
- `src/ui/dropdown.hpp:54`、`:78`：`DropdownList::owner_`
- `src/ui/menu_bar.hpp:426-436`：创建 menu scrim/popup
- `src/ui/menu_bar.hpp:99`：`MenuPopup::owner_`

`Dropdown` 和 `MenuBar` 都没有析构函数来 `close()`。如果它们在弹出层还打开时被父容器销毁（例如切换页面、清理内容、删除面板），会发生：

- `UIRoot` 的 overlay 仍持有 popup/scrim；popup 绘制时通过 `owner_` 访问已经销毁的 `Dropdown`/`MenuBar`；
- scrim 的回调 lambda 捕获了 `this`，点击空白或滚动时调用 `close()`，形成 UAF；
- 所有者自己的 `popup_`/`scrim_` 指针也变成悬空，后续 `is_open()` 仍可能返回真。

虽然 `UIRoot` 析构时 overlay 先于普通 children 销毁，能覆盖“整个 root 一起销毁”的情况，但覆盖不了“单个控件提前销毁”。

建议：

- 为两个控件添加析构函数，调用 `close()`；`close()` 必须在 owner 仍然有效时移除 overlay。
- 更好的方案是 popup 持有 owner 的弱令牌/节点 id；owner 失效后 popup 自行关闭，不直接解引用。
- 增加测试：打开 dropdown/menu，在不调用 `close()` 的情况下销毁 owner，随后 `tick()`/绘制不应 UAF。

### P1-5 `UIRoot::clear_overlays()` 立即销毁，绕过 `trash_` 和所有者状态

位置：`src/ui/root.hpp:22`

`remove_overlay()` 的注释明确说明需要延迟销毁，因为事件派发期间可能仍持有目标指针；但 `clear_overlays()` 直接：

```cpp
overlays_.clear();
mark_layout_dirty();
```

这会导致：

- `UISystem` 的 `hovered_`/`pressed_`/`focused_` 令牌失效，但同一 poll 中的后续事件仍可能使用裸指针；
- `Dropdown`/`MenuBar` 的 `popup_`/`scrim_` 和 `open_` 状态没有同步清空，后续绘制/交互访问已销毁 overlay；
- 外部持有的 `DialogHost*`/popup 指针立即悬空。

建议：

- 移除 `clear_overlays()`，或把它实现为把所有 overlay 移入 `trash_`，并在 layout 时统一销毁。
- 清理 overlay 前通知所有者状态，或让所有者不持有裸 overlay 指针，只持有令牌。
- 增加测试：打开 dropdown 后调用 `clear_overlays()`，再 `tick()`/绘制/点击，ASAN 下无错误。

### P1-6 公共头文件暴露 Vulkan，但 `cosine_text`/`cosine_ui` 没有 PUBLIC 传播 Vulkan 依赖

位置：

- `src/graphics/vertex.hpp:6-7`：`#include <vulkan/vulkan.hpp>`
- `src/graphics/drawable.hpp:3`：公共头 `#include "vertex.hpp"`
- `src/CMakeLists.txt:12`：`cosine_text` 只 PUBLIC 链接 `glm::glm freetype`
- `src/CMakeLists.txt:25-32`：`cosine_ui` 把 `Vulkan::Vulkan` 放在 PRIVATE
- 例如 `test/test_text.cpp` 链接 `cosine_text`，`test/test_ui_*.cpp` 链接 `cosine_ui`

Linux 上 Vulkan 头可能位于 `/usr/include` 默认搜索路径，所以问题不明显；Windows 上 Vulkan SDK 的 include 目录通常只通过 target 传播。一旦下游只链接 `cosine_text` 或 `cosine_ui`：

- 编译器找不到 `vulkan/vulkan.hpp`；
- 即使头文件能找到，Vulkan loader/库的链接也可能缺失；
- 测试和外部使用者会被迫自己 `find_package(Vulkan)`，破坏“静态库自动传播公共依赖”的设计目标。

建议：

- 将 `Vulkan::Vulkan` 改为 `cosine_text` 和 `cosine_ui` 的 PUBLIC 依赖；或者把 `Vertex` 的 Vulkan 类型移出公共头，改成普通顶点格式（位置/颜色/UV 使用自有类型），只在 backend 内部映射。
- 如果保留公共 Vulkan 头，至少让 `cosine_text` 和 `cosine_ui` 的 PUBLIC include/link 一致。
- 在 Windows CI 中增加一个只链接 `cosine_text` 的最小 test 编译检查，而不是只构建主程序。

### P1-7 `ColorRect` 在悬停/离开/滚轮时永久改写配置颜色

位置：`src/ui/color_rect.hpp:43-59`

`ColorRect` 是通用纯色矩形，但当前：

- `on_mouse_enter()` 把颜色改成硬编码蓝色；
- `on_mouse_leave()` 改成硬编码浅蓝，而不是恢复构造时颜色；
- `on_scroll()` 改成绿色，并且返回 `false`，事件没有消费但视觉状态已经改变。

它在 gallery 中用于颜色色块（`examples/ui_gallery/ui_gallery.hpp:378-379`、`:405` 等）和分隔线，因此用户只要把鼠标移过色块，色块就会变成与配置无关的蓝色/浅蓝/绿色；这是明显的控件语义错误，也容易让截图/验收结果不稳定。

建议：

- 保存 `base_color_`；hover 只改变临时绘制颜色，leave 恢复 `base_color_`；滚轮不应修改颜色。
- 如果确实需要可交互色块，新增明确的 hover/pressed 样式 API，而不是把调试行为写进通用控件。
- 增加测试：构造指定颜色，调用 enter/leave/scroll 后断言颜色恢复或保持预期状态。

## 6. P2：稳定性、性能、一致性和维护性问题

### P2-1 `Vbox`/`Hbox` 的 stretch 覆盖子控件 `max_size`

位置：`src/ui/vbox.cpp:179-181`、`src/ui/hbox.cpp:179-181`

grow 分支会考虑 `max_size`，但 stretch 分支在计算完可用宽度/高度后直接赋值：

```cpp
item.size.x = available_w;
```

或对应的 `item.size.y = available_h;`。这会让设置了 `max_size` 的子控件在交叉轴上被拉大，破坏“最大尺寸”约束。典型场景是固定宽度的按钮/输入框放在 stretch 的列里。

建议：stretch 赋值前调用 `child->clamp_size(...)`，或按 clamp 后的尺寸重新计算对齐；补布局测试。

### P2-2 `FontFace::set_pixel_size()` 不更新 `pixel_size_`，`metrics()` 用旧尺寸做除法

位置：`src/graphics/font_face.cpp:5-9`、`:36-37`、`:41-50`

`set_pixel_size()` 只调用 FreeType 的 `FT_Set_Pixel_Sizes`，没有同步成员 `pixel_size_`。之后如果调用 `metrics()`：

- 分子来自新 face 尺寸；
- 分母还是旧 `pixel_size_`；
- ascent/descent/line height 比例会错误。

目前 `Renderer` 主要在动态字形加载时反复切换尺寸，而且 metrics 多在初始构建时读取，所以问题可能潜伏；一旦有代码在动态 glyph 之后查询 metrics，就会得到错误行高。

建议：`pixel_size_` 与 face 状态保持一致；如果 `set_pixel_size()` 是 `const` 或懒加载语义，明确缓存 key，禁止在未同步成员的情况下暴露 metrics；补充“切换尺寸后 metrics 比例不变”的测试。

### P2-3 `FontAtlas::add_glyph()` 对超大字形只回绕一次，可能越界写图集

位置：`src/graphics/font_atlas.cpp:125-146`

当字形宽度加边距超过当前行剩余空间时，代码只回绕一次；如果 `width + 4 > tex_width_`，回绕后仍然放不下，但后续仍会写 `width` 像素到 `dst_x`，越过行尾。高度方向有 `pack_y_ + height + 2 >= tex_height_` 检查，但宽度没有对应的拒绝条件。此外 `pixel_size == 0` 时 `width_ratio`/`height_ratio` 的除法也有除零风险（`:154-155`）。

图集通常为 2048，普通字形不会触发；但小图集测试、异常字体或未来多字号图集可能触发内存破坏。

建议：

- 在回绕前检查 `width + 4 > tex_width_` 或 `height + 4 > tex_height_`，无法放入就直接返回 `false`，或自动扩大图集。
- 校验 `pixel_size > 0`，否则拒绝添加或使用安全默认值。
- 用 ASAN 运行一个“小图集 + 超宽 glyph”的回归测试。

### P2-4 动态字形图集每次 revision 全量上传，并在单次提交后 `waitIdle()`

位置：

- `src/backend/vulkan/renderer.cpp:308-335`：revision 变化时上传完整图集
- `src/backend/vulkan/renderer.cpp:466-476`：`end_single_time_commands()` 提交后立即 `graphics_queue().waitIdle()`

2048×2048 RGBA 图集约 16 MB；CJK 首次加载或交互过程中不断出现新字形时，每个 revision 都要全量 staging/copy，并同步等待 GPU。表现可能是首次打开中文界面、滚动列表或切换页面时卡顿。

建议：

- 记录 dirty rect，只上传新增/变化的区域；至少把上传合并到帧末一次。
- 使用独立传输队列或每帧最多一次上传，避免在绘制路径中 `waitIdle()`。
- 对动态字形做预算/节流，或者启动时预生成常用字符集。
- 用 FrameStats 增加“图集上传次数/字节数”指标，便于验收。

### P2-5 `SwapChain::recreate()` 在最小化时忙等 `glfwPollEvents()`

位置：`src/backend/vulkan/swap_chain.cpp:20-29`

窗口最小化后 framebuffer 为 `0x0`，`recreate()` 进入循环不断 `glfwPollEvents()`，会占满一个 CPU 核心，且没有超时/退避。虽然事件仍能被处理，但这是不必要的忙等。

建议：在 `0x0` 时直接返回/等待恢复，使用 `glfwWaitEventsTimeout()` 并降低轮询频率，或由窗口回调驱动重建。

### P2-6 `Window::init_window()` 不检查 GLFW 初始化/窗口创建，标准光标泄漏

位置：`src/backend/window.cpp:19-33`

`glfwInit()` 和 `glfwCreateWindow()` 的返回值都没有检查；失败后仍继续设置光标和创建 Vulkan surface，错误信息会非常间接。`GLFWcursor* cursor = glfwCreateStandardCursor(...)` 也没有保存和 `glfwDestroyCursor()`，`Window` 析构只销毁 window/terminate。

建议：

- 检查 `glfwInit()` 失败并抛出带错误码的异常；检查 window 为空。
- 保存 cursor 成员并在析构中销毁，或使用 GLFW 默认光标避免资源泄漏。
- 安装 `glfwSetErrorCallback`，把 GLFW 错误带入现有错误上下文。

### P2-7 `key_callback` 忽略 `GLFW_REPEAT`，长按 Backspace/Delete/方向键不重复

位置：`src/xel_application.cpp:92-105`

当前只在 `GLFW_PRESS`/`GLFW_RELEASE` 时构造事件，`GLFW_REPEAT` 被丢弃。结果是 TextInput 长按退格、删除、方向键时没有系统按键重复；对文本编辑体验影响明显。

建议：把 `GLFW_REPEAT` 也作为 `KeyDown` 派发，并在事件中标记 `repeat`；或者单独增加 `KeyRepeat` 事件，由 TextInput 决定是否消费。注意避免和 char callback 的换行/字符插入重复。

### P2-8 `Line`/`Triangle`/`Renderer` 直接绘制路径未预乘 alpha，和管线混合不一致

位置：

- `src/backend/vulkan/renderer.cpp:147-157`：管线使用预乘 alpha 混合
- `src/graphics/rectangle.hpp:24-27`：矩形已预乘
- `src/graphics/line.hpp:43-46`、`triangle.hpp:23-25`：颜色原样写入
- `src/backend/vulkan/renderer.cpp:747-789`：`draw_rect`/`draw_rect_uv`/`draw_triangle` 也原样写入

对 alpha < 1 的线/三角形/直接 draw 调用，RGB 没有乘 alpha，配合 `One/OneMinusSrcAlpha` 会显得过亮。当前多数 UI 颜色不透明，所以问题不总是可见，但公共 primitive 行为不一致。

建议：统一在写入顶点前做 `rgb *= a`，或统一由 shader 负责直通 alpha 并在 pipeline 使用对应混合；不要只修 Rectangle。

### P2-9 `Table::row_at()` 包含滚动条区域，点击条会选中下方行

位置：`src/ui/table.hpp:359-367`

`row_at()` 的 x 范围到 `global_.pos.x + global_.size.x`，没有排除右侧滚动条区域。表格本身没有滚动条拖动，因此用户点击滚动条时：

- 行选择会变化；
- hover 高亮落在被条遮住的行上；
- 滚动条看起来像“点击选中行”的装饰，而不是滚动控件。

建议：`row_at()` 排除 `bar_w`；如果表格需要滚动条交互，增加拖动/轨道点击，并让 bar 区域优先处理。至少不要把 bar 点击解释为行选择。

### P2-10 `MenuScrim::on_mouse_down()` 总是关闭，点击另一个菜单标题需要点两次

位置：`src/ui/menu_bar.hpp:72-76`（scrim 点击即 dismiss）、`:276-282`（`MenuBar::on_click`）

菜单打开时，全屏 scrim 位于普通菜单栏之上，点击任何位置都会先命中 scrim 并关闭菜单。虽然鼠标移动到另一个标题时 scrim 的 hover 逻辑可能先切换菜单，但点击另一标题仍会被 scrim 当作“点击空白”处理。典型行为变成“先移动切换，再点击关闭”，不符合菜单栏常见交互。

建议：scrim 的鼠标按下如果落在菜单栏标题区域，不 dismiss，而是转发给 `MenuBar` 处理；或者让菜单栏本身在 overlay 层之上且优先命中。

### P2-11 文档测试数量滞后，README 仍是最小草稿

位置：

- `docs/project_assessment.md:9`：写“14 个测试通过”
- `docs/project_assessment.md:16`：写“`ctest` 20/20 通过”
- `docs/project_assessment.md:46`、`:131`：仍写 20/14 个测试
- 当前 `test/CMakeLists.txt` 有 25 个 `add_test`

这不是代码缺陷，但会让评审/发布判断使用过期数据。建议在下次文档整理时统一为当前注册测试数，并明确 `testglfwinit` 是否需要图形会话、是否需要注册。`README.md:1-4` 仍是两行式草稿，建议作者确定是否保留“interpreter”定位，避免与当前 GUI 框架主线混淆。

## 7. 构建与发布风险（与代码缺陷分开）

### 7.1 CMake 4.0 门槛

`CMakeLists.txt:1` 要求 `cmake_minimum_required(VERSION 4.0.0)`，`docs/ci.md:69` 也明确承认镜像需要满足该版本。当前服务器 CMake 3.25.1，无法进行本报告的完整构建验证。

这不等于“服务器缺依赖”就是代码 bug；需要项目做一次明确决策：

- 如果 C++ module scan 是硬需求，保留 4.0 并要求 CI/开发环境升级；
- 如果希望兼容 Debian 12 等 CMake 3.25 环境，需要评估 `CXX_SCAN_FOR_MODULES` 的替代路径（该属性至少需要 CMake 3.28，不能简单改成 3.20）；
- 无论选择哪条，建议在 `README`/`docs/ci.md` 中写出最低版本和验证命令。

### 7.2 字体与 CJK 的部署假设

仓库不随包携带 CJK 字体，`SPEC`/`docs/packaging.md` 依赖系统字体或 `COSINE_CJK_FONT`。这是有意的部署策略，不是缺陷；但需要在发布说明中明确：

- 没有 CJK 字体的机器会回退到 `assets/fonts/default8.png`，中文显示能力受限；
- 图集构建/动态加载依赖字体配置，首次启动可能更慢；
- 发行包应验证目标系统常见字体路径，或提供可选字体包方案。

### 7.3 Windows 实测

`docs/ci.md:68` 说明 Windows job 目前只做构建与单元测试，没有窗口级运行冒烟。结合 P1-6 的 Vulkan 公共依赖问题，建议在 Windows 上至少增加：

- 只链接 `cosine_text`/`cosine_ui` 的最小测试目标编译；
- Vulkan SDK include 路径不在全局时的构建验证；
- 窗口创建/字体回退/swapchain 重建的冒烟。

## 8. 建议的修复顺序

1. **先做 P0-1/P0-2**：统一事件派发与延迟结构性变更；这是所有控件回调安全的前提。
2. **再做 P0-3**：顶点容量预检，避免大场景直接内存破坏。
3. **P1-1/P1-2/P1-3**：修 `ScrollView` 的视口/命中/`ScrollPanel` 默认尺寸，这三项直接影响 gallery 和所有可滚动页面。
4. **P1-4/P1-5**：overlay 所有者和 `clear_overlays()` 生命周期，建议和 P0-1 的延迟回收一起设计。
5. **P1-6**：修 CMake 公共依赖；这是 Windows/下游使用的交付阻塞项。
6. **P1-7 + P2-1**：控件样式和布局约束的语义修正，成本低、回归风险小。
7. **P2 字体与渲染**：字体面/图集边界、图集上传、预乘一致性可以按性能/画面验收分批做。
8. **P2 窗口/输入/文档**：窗口初始化、按键重复、表格/菜单交互、文档同步，安排在稳定性收尾阶段。

## 9. 修复验收建议

当前环境无法执行完整构建，以下命令供有 Vulkan SDK、CMake 4.0 的环境使用：

```bash
# 常规 Debug 构建
cmake -S . -B build-review -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build-review -j2
ctest --test-dir build-review --output-on-failure

# ASAN 构建/测试
cmake -S . -B build-review-asan -G Ninja \
  -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_CXX_FLAGS="-fsanitize=address -fno-omit-frame-pointer" \
  -DCMAKE_EXE_LINKER_FLAGS="-fsanitize=address"
cmake --build build-review-asan -j2
ASAN_OPTIONS=detect_leaks=1 ctest --test-dir build-review-asan --output-on-failure

# 关键回归子集
ctest --test-dir build-review -R 'test_ui_(events|dropdown|scrollbar|layout|text_input|gallery)' --output-on-failure
```

建议新增的回归用例：

- 回调中销毁自身/父节点/祖先节点，覆盖 mouse down/up/click/scroll/key；
- 超过 65,536 个 quad 的容量预检；
- 双轴滚动条从单轴状态切换、条消失后的视口恢复；
- 滚动条下方按钮的命中顺序；
- 不设置 min/max 的 `ScrollPanel` 高度；
- 打开 dropdown/menu 后销毁 owner，以及 `clear_overlays()` 后再 tick/绘制；
- `ColorRect` 的 enter/leave/scroll 颜色状态；
- `FontFace` 切换字号后的 metrics 比例；
- 小图集加超宽字形；
- Windows 下只链接 `cosine_text`/`cosine_ui` 的最小编译目标。

- IME/预编辑文本未接入（`SPEC.md` 明确留到后续）。
- 按词换行、CJK 标点避头尾、shaping 尚未实现；当前换行以字符/词边界的基础能力为主，属于 T6 后续工作。
- 多行 `TextInput` 目前只对光标所在行做水平滚动，非光标行的长文本可见性有限；独立水平滚动条也在后续计划中。
- CJK 字体不随包分发，依赖系统字体或 `COSINE_CJK_FONT`。
- Vulkan 公共图元仍通过 `active_font_atlas()` 使用全局字体图集，多 Renderer/多上下文场景尚未完全去全局化；这属于已知架构迁移，不是本次的崩溃问题。

---

**总结**：当前最需要优先解决的不是“再加控件”，而是事件生命周期和渲染容量这两条底层边界；随后处理滚动视口/命中、overlay 所有者和 CMake 公共依赖。完成这些之后，现有的组件扩展和 CJK 文本能力才有稳定的运行基础。
